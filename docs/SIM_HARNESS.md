# AI 玩家模擬器（原生內核 headless）

> **地圖改名（2026-08-07）**：本文件以下內容寫於改名前。第 1 張地圖「草原 `plains`」現為「荒漠 `desert`」，
> 第 2 張「荒漠 `desert`」現為「冰原 `Icefield`」。**`desert` 換了指涉對象**，閱讀舊紀錄時請據此對照（見 PATCH.md）。

## 這是什麼

用**遊戲本體的程式碼**跑 AI 玩家掛機模擬。所有數值——傷害、掉落、經驗、成本、機率、
日誌文字——都由遊戲自己算；harness 只負責推進時間、在決策點問策略、把指令送進遊戲。

harness 內沒有任何遊戲公式或常數。這不是靠自律，是靠結構（見「隔離」一節）。

## 怎麼跑

```bash
node --max-semi-space-size=64 scripts/run_sim.js --hours=100 --seed=20260730
```

| 腳本 | 用途 |
| :--- | :--- |
| `scripts/run_sim.js` | 主模擬，輸出存檔／快照 CSV／原生事件／執行摘要 |
| `scripts/bench_sim.js` | 純效能量測（無策略） |
| `scripts/verify_equivalence.js` | 決定論 + 改造等價性 + 種子敏感度 |
| `scripts/test_policy_isolation.js` | 策略層隔離反證（每項都必須失敗） |
| `scripts/cross_check.js` | 真瀏覽器 ↔ headless 逐檢查點比對 |
| `scripts/verify_trace.js` | 真人錄製 ↔ 軌跡重播逐檢查點比對（見「真人基準線」） |
| `scripts/compare_runs.js` | 兩場模擬的曲線對照（真人 vs AI） |
| `scripts/proxy_guard_ab.js` | Proxy 守門方案的行為中性 A/B 判定 |

策略檔（資料，非程式）：

| 檔案 | 用途 |
| :--- | :--- |
| `scripts/sim/policy.default.json` | 從零開始的掛機策略。看成長曲線用這份 |
| `scripts/sim/policy.lategame.json` | 以 GM 墊出已轉生角色，專門驗證天賦／神鑄／高塔會不會動。**不能拿來談成長曲線** |

`--max-semi-space-size=64` 是 GC 調參，實測比預設快約 1.4 倍，不影響結果。

輸出在 `sim_out/`（已 gitignore）：

- `save_final.json` — 可直接匯入遊戲續玩
- `snapshots.csv` + `snapshots.meta.json` — 圖表資料與**每一欄的來源標註**
- `native_events.jsonl` — 遊戲原生 blog/flog/loot/notice 事件（非 harness 自組）
- `run_summary.json` — 效能實測、指令統計、事件計數、狀態雜湊

## 架構

```
run_sim.js（驅動）
   │  推進時間 → engine.step(n)          每步 dt = TICK_MS/1000 = 0.1s，不放大
   │  觀測     → engine.view()           = 原生 buildView()
   │  決策     → policy.decide(深拷貝)    隔離 context，見下
   │  送指令   → engine.cmd(name, args)  = 原生 runCommand()
   ▼
sim/engine.js（宿主）
   │  把 js/worker/sim.worker.js 原封不動載進 vm context
   │  它自己 importScripts 那 20 支模擬層檔案，載入順序與線上完全一致
   ▼
遊戲本體
```

### 只替換「瀏覽器環境」，不替換遊戲

| 替換項 | 為什麼 |
| :--- | :--- |
| `Math.random` → 種子化 PRNG | 沒有決定論，任何比對都做不下去。單一注入點，公式檔案一行不改 |
| `Date` / `performance` → 虛擬時鐘 | **關鍵**：`js/item.js:263` 的寶石商店與 `js/forge.js:486` 的熔煉完成都讀真實時鐘。縮時上千倍時真實時鐘幾乎沒走，這兩個系統會整場靜止 |
| `postMessage` / `importScripts` / `setTimeout` | Worker 環境替身 |

### 時間推進的正確性

- 步長固定 `0.1s`，與線上 `TICK_MS` 相同。**放大 dt 換速度＝換一個遊戲**，不做。
- 每 2 步（模擬時間 5Hz）跑一次 `loop()` 的 `updateShownRes` / `maintainGemShop` /
  `checkForgeUnlockNotice`。這三支不在 `simStep` 內，但會刷新寶石商店與解鎖熔爐，
  只呼叫 `simStep` 會讓這兩個系統整場不動。

## 隔離：策略層碰不到遊戲狀態

策略跑在一個**沒有 `G`、沒有 `FIELD`、沒有 `require`、沒有 `process`** 的獨立 vm context，
只拿得到 `buildView()` 的深拷貝，只能回傳「指令名 + 參數」。

這是**能力剝奪**，不是執行期偵測。拿不到參照的東西不需要被監控。

`scripts/test_policy_isolation.js` 逐項反證（12 項全部必須失敗），並附對照組確認策略仍能正常決策。
`Math.random` 與 `Date.now` 在策略 context 內被改成呼叫即拋錯——策略有隨機性或讀真實時間，決定論就沒了。

### 為什麼不用 Proxy 包住 G

1. 包不住。戰鬥狀態在 `js/combat.js:5` 的 module-level `FIELD`，不在 `G` 裡。
2. 成本壓在每次屬性存取上，而要防的事只發生在決策的那一瞬間。
3. **會改變遊戲行為。** `js/battlefield.js:186` 的 `bfLiveList(...).indexOf(locked)` 與
   `js/combat.js:665` 跨 tick 持有的 `_lockTarget` 都依賴物件識別比對，
   每次 `get` 新建 Proxy 會讓比對必定失敗。

第 3 點不是推論，`scripts/proxy_guard_ab.js` 實測過（見下）。

| 檢查 | 結果 |

| 既有測試 664 支 / `npm run build` | ✅ 全綠 |

### 交叉驗證（最有力的一道）

seed=779，真 `index.html` + 真 Worker + 真 IndexedDB，跑 55 遊戲秒，每 0.2 秒一個檢查點，
`buildView()` 全部 24 個欄位逐欄比對：**275 個共同檢查點完全一致**。

harness 只要在任何地方偷算過一次，這裡就會分岔。

**做法**（Antigravity 要重跑時照這個順序）：

1. `preview_start` 起本機伺服器（`.claude/launch.json` 已有多組 port）
2. 瀏覽器開 `http://127.0.0.1:<port>/index.html?seed=779`
   ⚠️ 用 `127.0.0.1` 而不是 `localhost`——不同 hostname 是不同 origin，
   才不會去讀（或覆寫）既有存檔
3. 在頁面上掛收集器：
   `window.__x={rows:[]}; WorkerBridge.on('tick',m=>m.view&&__x.rows.push(m.view))`
4. 讓它跑 1 分鐘以上，把 `JSON.stringify(__x.rows)` 存成檔案
5. `node scripts/cross_check.js <那個檔案> 779`

**測試模式的差異（必須連同結果一起說明）**

帶 `?seed=N` 且 hostname 為本機時，Worker 會進入決定論測試模式
（`js/worker/sim.worker.js` 檔頭 `installTestSeed`），與正式遊玩有三處差異：

1. `Math.random` 換成種子化 mulberry32
2. 每個計時器週期固定走一整步，不補欠帳、不走殘步
3. 維護區塊（`updateShownRes`/`maintainGemShop`/`checkForgeUnlockNotice`）改以**步數**計時
4. 一律以全新角色開機，不讀存檔、不落地存檔

**第 2、3 點不是可有可無的**。正式路徑每輪最後會走一個不足 0.1 秒的殘步，
長度取決於真實計時器抖動——連同一個瀏覽器跑兩次都不會一樣，比對在結構上就做不到。
維護區塊照真實時間跑也有同樣問題：`maintainGemShop` 首次會呼叫 `rollGemShop()` 消耗亂數，
它落在第 2 步還是第 3 步會讓整條亂數序列岔開。

所以這道驗證證明的是「headless ≡ 測試模式的瀏覽器」，兩者與正式遊玩的差距就是上面那幾項。

## 效能

實測（Windows / Node，`--max-semi-space-size=64`）：

| 項目 | 數值 |
| :--- | :--- |
| 吞吐 | 約 10,000～12,000 步/秒 |
| 縮時倍率 | 約 1,000～1,200x |
| 10 遊戲小時 | 34.5 s |
| **100 遊戲小時** | **約 5.7 分鐘** |

倍率是**量測值**，每次 `run_sim.js` 都會把實測寫進 `run_summary.json`，不是設定值。

⚠️ 上面那組數字是**沒有策略**的純模擬吞吐（`bench_sim.js`）。開了 ROI 策略之後
主導成本完全不同——見下一節。

已做的優化（全部經雜湊驗證等價）：

1. `js/worker/sim.worker.js` 的 `updateShownRes` 加上 early-skip——旗標設了就不再重算。
   改造前它（含 `totalGemsAll`）佔 headless 總 CPU 的 **39%**，只為決定頂欄圖示要不要顯示。
   瀏覽器端每秒也跑 5 次，玩家機器同樣受益。
2. `Math` 用自有屬性複本而非 `Object.create(Math)`，避免每次 `Math.floor` 走原型鏈。
3. GC 調參。

## ROI 策略下的成本結構：八成不在遊戲裡（2026-08-03）

一場 20 小時的 ROI 模擬只有 **1,677 步/秒**，而純模擬是 10,000～12,000。
也就是**每 6 步裡有 5 步的時間是花在 harness 上**。深局狀態
（Lv.182／關卡 145／背包 270 件）的 profile：

| 區塊 | 佔比 |
| :--- | ---: |
| `panels.eval` | **47%**（換裝精算 23／詞條 ROI 12／身上詞條 11） |
| `simStep`（真正的遊戲） | 17～20% |
| `panels.inv` | **16%** |
| `policy.decide` 的 JSON 深拷貝 | 6% |

再往下拆：`computeStats` 佔 41%，而它內部**天賦查找 17%、詞條數值鏈 16%、
`itemScore` 15%**。根因是同一件事：評估器每次規劃要跑約 47 次 `computeStats`，
而 13 個部位裡只有 1 個不一樣——其餘 12 個被重算了 47 遍。

### 四項改造（0.25 遊戲小時，深局，單行程，取三次中位）

| | 時間 | 相對 | 存檔雜湊 |
| :--- | ---: | ---: | :--- |
| 改造前 | 5.13 s | 1.00x | 基準 |
| ① 天賦：`talentStatBonuses` 把 levels 表／節點清單／全滿倍率提出迴圈 | 4.4 s | 1.17x | 相同 ✅ |
| ②③ 詞條：`affixBaseValue` / `affixValue` 在**規劃期間**記憶化 | — | — | 相同 ✅ |
| ①②③ 合計 | 4.1 s | 1.25x | 相同 ✅ |
| ④ `inv` 面板不建 `items` 投影（ROI 策略從不讀它） | 3.05 s | 1.68x | 見下 |
| ⑤ 背包掃描結果跨規劃快取 | **2.7 s** | **1.90x** | 相同 ✅ |

背包愈大差距愈大（400 小時的常態水位是 850 件左右）：

| 背包件數 | 改造前 | 改造後 | 倍率 |
| ---: | ---: | ---: | ---: |
| 270 件（20 小時的現況） | 5.2～6.1 s | 2.7～3.0 s | **1.9x** |
| 850 件（400 小時的水位） | 8.0 s | 3.2 s | **2.5x** |

實測總吞吐（8 行程並行，i7-11800H）：**12.7 → 21.4 遊戲小時/分**。
400 小時 × 5 seed 的牆鐘推估：**約 2.9 小時 → 約 1.5 小時**。

### ① 天賦：640 次等級查找裡有 632 次是重複的

`talentStatBonuses` 原本每個節點各呼叫一次 `talentCompleteMultiplier`，
而它內部要查 8 個節點的等級。80 個節點就是 640 次查找，其中 632 次重複。
再加上 `talentList()` 每次重建 80 個物件的陣列、每次 `talentLevel()` 都重跑
`talentState()` 的初始化檢查。

改法是純重構（沒有快取、沒有失效問題）：levels 表取一次、節點清單建一次
（`TALENT_TREES` 是 `js/data.js` 的靜態設定表）、每一轉的全滿倍率算一次。
`tests/talents-perf-equivalence.test.cjs` 拿**改造前的寫法**當參照實作逐欄比對，
而且刻意涵蓋「某一轉剛好全滿」那個 ×2 的邊界——只比「都沒點」的話，
那個倍率永遠是 1，改壞了測不出來。

### ②③ 詞條記憶化：為什麼**不能**放進 `js/formula.js`

第一版改在 `js/formula.js`，被既有測試擋下來，而且擋得對：

- `tests/affix-roll-storage.test.cjs` 的「調整參數表的基礎值／成長基礎值後，
  同一強度值算出新數值」會**就地改 `AFFIX_POOL.atkFlat.base`** 再要求數值跟著變。
  參數調整回溯生效到舊存檔是**設計要求**，一個永久快取會靜靜違背它。
- 重排 `affixBaseValue` 的內文還會讓 `apply_params` 的錨點對不上那幾格
  （`tests/apply-params*.test.cjs` 紅燈）——參數表是靠原始碼的文字樣式定位的。

所以改放在 `scripts/sim/evaluator.js`，只在**一次規劃期間**安裝、`finally` 卸載。
那一段是純讀取的（流進遊戲函式的裝備一律先過 `evalSafeItem`），而 47 倍的冗餘
也全部發生在那裡面。離開那一段就還原成遊戲原本的函式，參數一調下一次規劃立刻反映。

實測這個「小範圍」版本在 ④ 之後拿到的收益與全域快取**完全相同**（3.05s vs 3.1s）——
`inv.items` 拿掉之後，規劃區塊外面本來就沒剩多少詞條計算。

### ④ 面板投影：ROI 策略從來沒讀過那份背包清單

`panels.inv.items` 要對每一件跑一次 `inventoryCellView`＋`itemScore`，
深局 300 件時單次 4.4 ms、每 5 遊戲秒一次，再加上 129KB 的序列化與深拷貝。
而 ROI 策略**一次都沒讀過它**——它的換裝走 `panels.eval.slotUpgrades`
（問遊戲「穿上去戰力升不升」），所以沒有 `bestPerSlot` 規則。其餘六份策略都還在用。

機制：策略以 `panelParams` 宣告，`buildInventoryPanel` 認 `params.items === false`。
`scripts/sim/policy.js` 的 `assertPanelParams` 在載入時擋下「宣告了不建、卻又有
規則指到它」——那種錯誤不會壞掉，只會讓規則永遠取不到值而靜靜失效。

⚠️ 這一項會讓存檔雜湊**改變**，而原因本身是個發現：`itemScore()` → `itemEnchants()`
會把 `{enchant: null}` **就地**正規化成 `{enchants: []}`。所以「建一次背包面板」
這個看起來純讀取的動作其實會改存檔。實測兩份存檔的差異**只有** 3 件剛掉落、
還沒被任何其他路徑碰過的物品的這個欄位，等級／關卡／背包件數／其餘欄位逐位元組相同。
（`evalSafeItem` 早就在替評估器防這件事，但 `buildInventoryPanel` 這條路徑沒有防。）

### ⑤ 背包掃描的跨規劃快取：這一項才是「愈到後面愈慢」的解

背包裡的裝備**待在背包的期間是不動的**——強化、洗煉、鑲嵌、附魔的對象都是身上那套，
掉落是新物件，穿上去就離開背包。所以評估器每 15 秒把整份背包重新複製、重算可用部位、
重跑一次 `itemScore` 是純浪費，而且成本與**件數**成正比。

失效判斷用**物件識別**，不是「記得在改東西的時候去清快取」——後者漏一個寫入點
就會靜靜沿用舊分數，而症狀只是「AI 挑了比較差的那件」。`itemScore` 讀到的每一個
可變輸入都記下來比對：強化等級／稀有度／裝等是純量，詞條、寶石、附魔、傳奇特效、
神鑄特效比對陣列與每一個元素的識別。遊戲改這些東西一律是換物件或換整個陣列
（`rerollSingleAffix` 指派新物件、`rerollItemAffixes` 重建陣列、鑲嵌是 `sockets[i] = gem`、
附魔是 push），所以識別比對抓得到全部。

`tests/sim-bag-cache.test.cjs` 對每一種會改變分數的欄位各改一次，分數都必須跟著變。
⚠️ 寫這支測試時踩到一次：附魔物件的形狀是 `{key, gemLv}`（數值由當下的寶石等級
當場算出），寫成 `{key, level}` 的話 `enchantValue` 會走凍結值那條路回 0——
於是分數不變、測試「通過」，而它其實一個東西都沒測到。所以那一項先斷言
`enchantValue(...) > 0` 當前提。

### 還沒做的：`computeStats` 的逐件貢獻拆分

同一份裝備被重算 47 次這件事，記憶化只解掉了詞條數值那一層。真正的解法是把
`computeStats` 拆成「每件裝備的貢獻 → 聚合」，讓評估器換一個部位時只重算那一件。
收益很大（47 次 → 1 次＋13 個差量），但那是動出貨公式的重構，風險不小。

## 背包水位：一條「比例門檻」把上限變成了成本（2026-08-03）

### 格數不花錢，但它決定了件數

成本只跟**實際件數**有關——1000 格裡放 100 件與 100 格裡放 100 件完全一樣。
問題是件數不會停在 100：背包**唯一**會被清空的時機是策略的壓力閥
`salvage-when-bag-full`，而它的判斷式是

```
件數 / 上限 ≥ 0.9
```

用的是**比例**。於是上限就是水位線：上限 325 就填到約 290 才清，
而策略的 `buy-inv-upgrade` 寫著「逐步解鎖至 1000 格」。實測 20 小時的件數是鋸齒狀的：

```
 1h: 41   2h:116   3h:136   4h:149   5h:160   6h:172   7h:184
 8h: 58 ← 壓力閥啟動          16h:265  17h: 77 ←再清   20h:267
```

平均約 150 件，峰值貼著上限走。**上限拉到 1000 之後，同一條規則會讓峰值變成 900。**

而那條閥的目的本來就不是背包管理，它自己的註解寫著是為了防掉落管線回堵。
「背包平常該維持多小」這件事從來沒有被設計過——**這是缺口，不是決定**。

成本（做完面板投影之後，0.25 遊戲小時，深局）：

| 背包件數 | 時間 |
| ---: | ---: |
| 850 件（400h 的常態水位） | 3.1 s |
| 270 件（20h 的現況） | 2.6 s |
| 77 件 | **2.4 s** |

### 判準：問遊戲，不要用太古數

直覺的判準是「同部位同品質、太古數沒比較多就直接拆」。實測那會在**裝等分段邊界**
出事——用遊戲自己的公式算（R5、`atkFlat`、強度中間值）：

| | 一條詞條 | 整件（5 條） |
| :--- | ---: | ---: |
| 裝等 100、含 1 條太古 | 1,437 / 887 | 4,985 |
| 裝等 150、**0 條太古** | 1,327 | **6,635（+33%）** |

一條太古 ≈ ×1.62，跨一個裝等分段 ≈ ×1.50。所以跨過關卡 150 的那一刻，
「太古數沒比較多就拆」會把**強 33% 的新掉落當場拆掉**。
這正是本文件記過兩次的形狀：把「通常成立的偏好」寫成了「永遠成立的否決」。

改成問遊戲：`panels.eval.deadStock` 用 `itemScore`（背包滿載捨弱留強用的同一把尺，
裝等與強化倍率都含在裡面）排序，**在每一個穿得上的部位都排不進前 K 名**的才算死庫存。

這個判準與換裝決策是**對齊**的：`evalSlotUpgrades` 只精算每個部位前
`candidatesPerSlot`（預設 2）名，排在 K 名之外的候選本來就不可能被精算到。
K 取 5 是留給「前面幾件被穿走之後名次往上遞補」與「戒指類兩個部位共用候選」的餘裕。

### 兩個不能省的地方

- **`item.salvage` 不檢查 `locked`**（`js/worker/sim.worker.js`：解析到 id 就 splice 掉）。
  鎖定保護只在 `evalBagSweep` 的那一行 `if (!raw || raw.locked || raw.kind !== 'equip') continue`。
- **清單長度有上限**（`maxPerRefresh`），截斷數量如實回報在 `total` / `truncated`。
  「還有 300 件沒列出來」與「只剩 3 件」在報表上必須分得出來。

### A/B 實測：機制照設計運作，但成績沒有變好（8 seed × 20 小時）

| 指標（最小 / **中位** / 最大） | A 不清理 | B 清理 |
| :--- | ---: | ---: |
| 等級 | 51 / **177** / 219 | 55 / **110** / 294 |
| 最高關卡 | 50 / **150** / 164 | 50 / **100** / 200 |
| 物攻 | 370 / **73,981** / 129,634 | 462 / **32,966** / 162,326 |
| 背包平均件數 | 126 / **153.5** / 212 | 62 / **65** / 67 |
| 背包峰值 | 267 / **300** / 311 | 75 / **81.5** / 89 |
| 縮時倍率 | 155 / **168** / 200 | 174 / **183** / 192 |

機制本身完全照設計運作：背包穩定壓在 65 件、峰值不再貼著上限走、縮時 +9%。
但中位成績掉了一截。

**那個差距沒有被證實是因果。** 逐 seed 的曲線顯示兩臂在前 10 小時互有領先、
之後往**兩個方向**分岔——seed 230266939 是 B 從關卡 50 一路推到 190、A 卡在 50；
seed 230266934 正好相反。兩臂各有 2/8 個 seed 卡在關卡 50（第一個裝等分段的老問題），
中位數的落差主要來自那個雙峰落在哪一邊。平均值的差距只有一成
（等級 146 → 130、關卡 120.5 → 110.3），以這個變異數與 n=8 來說遠不到能下結論的程度。

**所以結論是「沒有證據支持」，不是「證實有害」。** 而它換到的 +9% 速度，
已經被 ⑤ 的背包掃描快取（不改行為、雜湊相同）整碗拿走了——**沒有理由承擔這個風險**。

### 目前的設定

機制預設**關閉**：`evalConfig.deadStock` 沒宣告就回 `null`，六份策略行為完全不變。
要啟用只需在 `evalConfig` 加 `{"keepPerSlot": 5, "maxPerRefresh": 50}`，
並加一條 expand 到 `panels.eval.deadStock.items` 的 `item.salvage` 規則。
`tests/sim-dead-stock.test.cjs` 盯著判準（含 locked 保護與截斷回報），機制不會腐爛。

⚠️ 要重跑這個 A/B 的話，**先把「兩臂各有 2/8 卡在關卡 50」那件事修掉**。
在那個雙峰還在的前提下，任何 8 seed 的中位數比較都會被它主導——
這正是本文件記過的「單一 seed 比較會得到相反的結論」的同一種陷阱，只是換成中位數。

## 遊戲改版時要不要同步給模擬器？

**預設：不用。** 數值、公式、常數、機率、掉落表、失敗訊息全部是從遊戲讀的，
改了模擬器隔天自動跟上。連寶石種類都是 `{"path": "panels.gems.gems"}` 取出來的，
新增第 39 種寶石不需要改任何清單。

但有三件事改了會讓模擬**靜靜失真**——不是壞掉，是安靜地測不到。
所以不靠「記得同步」，改成三個會自己叫的哨兵：

| 會失真的情況 | 哨兵 | 在哪裡看 |
| :--- | :--- | :--- |
| `loop()` 新增第四支維護函式，headless 沒跟上 | `tests/sim-harness-sync.test.cjs` | `npm test` 直接紅燈 |
| 面板欄位改名，策略的 `$path` 指到舊路徑 | 路徑解析失敗計數 | `run_summary.json` 的 `badStatePaths`，跑完也會印在終端 |
| 新增玩家指令，策略沒有對應規則 | 指令覆蓋率 | `run_summary.json` 的 `untestedCommands` |

第三項不一定是問題（有些指令本來就不該由 AI 用），但它是「策略還沒覆蓋什麼」的客觀清單——
遊戲新增系統時，新指令會自動出現在那裡，等於待辦清單自己長出來。

前兩項都做過反證測試，確認**真的會叫**：
故意從 `MAINTENANCE_FNS` 拿掉一支 → 測試紅燈並指出差異；
故意把 `panels.tower.tower.highest` 打成 `highestFloor` → `badStatePaths` 抓到。

## 指令成效怎麼讀

`run_summary.json` 的 `commands` 分成四類，**不要只看「送出」**：

| 欄位 | 意思 |
| :--- | :--- |
| `effective` | 真的做到了 |
| `noEffect` | 沒做到，`reasons` 是**遊戲自己給的原話**（如「技能點不足」「金幣不足（需要 5.02K）」） |
| `unknown` | 指令無回傳值（如 `js/tower.js:95` 的 `startTowerAuto`），要看原生日誌才知道結果 |

⚠️ 模擬層的回傳慣例與直覺相反：**`null` 是成功、字串是失敗原因**
（`js/skills.js:2129` 成功時 `return null`，失敗時 `return '技能點不足'`）。
天真地判斷 truthy 會把 1200 次失敗全部算成成功——這個坑踩過一次。

## 目標與缺口：讓策略自己發現該補什麼

策略原本寫的是**「該做什麼」**——一份靜態的詞條保留清單。問題是正確答案會隨關卡改變：
怪物閃避在關卡 130 是 86.8%、關卡 150 是 103%，而命中公式夾在 5%～100%。
所以命中率詞條在關卡 100 不需要、在關卡 146 是唯一解——**任何固定名次都是錯的**。

實測後果：角色面板命中 100%、身上 65 條詞條一條命中率都沒有，有效命中觸底 5%，
13,718 次出手只中 551 次。而策略完全不知道，它以為自己物攻 91K 很強。

改成宣告**「要達成什麼」**（`policy.targets`）：

```json
{
  "id": "hit",
  "kind": "selfMinusEnemy",
  "self": "panels.equip.stats.hit",
  "enemy": "ctx.enemyDodge",
  "clampMin": 5, "clampMax": 100,
  "atLeast": 95,
  "affixKey": "hit",
  "avoidSlots": ["ring", "amulet"],
  "preferSlots": ["boots", "legs", "wrist", "helmet", "gloves"],
  "maxAffixes": 4
}
```

直譯器每個決策點算出缺口掛在 `ctx.deficit.<id>`，`rerollForDeficit` 規則據此主動洗出
補缺口的詞條，補滿自動停手。**不需要有人回去改清單。**

實測（重度、100h 牆鐘、4 個 seed）：

| | 等級（最小/中位/最大） | 關卡（最小/中位/最大） |
| :--- | :--- | :--- |
| 無目標 | 105 / **161.5** / 454 | 133 / **149** / 206 |
| 缺口驅動 | 185 / **242.5** / 305 | 173 / **177.5** / 207 |

中位數關卡 149 → 177.5，最差的一次從 133 拉到 173，散佈明顯收窄。
⚠️ 對照組有一次跑到 Lv.454——那是運氣。**單一 seed 比較會得到相反的結論**，
這類判斷一律要多 seed。

### 三個實測踩過的坑

- **可用部位一律從遊戲讀**（`panels.equip.affixRules`，協議 v15），不要在策略裡手抄。
  抄過一次就錯了：寫了 `weapon`（命中率不能出現在武器上）與 `bracers`（遊戲的鍵是
  `wrist`），375 次洗煉一條都沒洗出來，而且沒有任何錯誤訊息。
- **試次只能算「真的洗到了」的**。策略層看不到指令結果，但看得到詞條有沒有變。
  不分辨的話，資源不足的空轉會把試次燒光然後永久放棄——實測 832 次嘗試有 579 次
  是資源不足，於是所有部位在沒洗到半次的情況下被判死刑。
- **不要讓「缺口未補滿」永久改變行為**。試過在缺口未補滿時禁止換掉帶有該詞條的裝備，
  結果從關卡 190 掉到 117：目標訂了達不到的值，於是保護變成永久凍結，裝備停止升級。
  任何「缺口未補滿時就……」的規則都要能在目標達不到時自己收手。

## 產出閘門：一場關於「誘因」而不是「策略」的實驗

> **現況（2026-08-02 決策）**：離線收益維持原本的設計——**以歷史最高關卡為基準的
> 固定費率**，不看命中率、不看怪物血量、也不看玩家傷害。強度改由參數表調整
> （見下方「參數表旋鈕」）。因此**六份策略的產出閘門都關閉**：在這個誘因結構下
> 它實測會讓成績變差。要啟用只需在 `stageGate` 加 `requireTargets` / `targetRetreat`
> 兩個欄位，機制與測試都在。
>
> 這一節照時間順序保留，因為那個順序本身就是結論：
> **策略怎麼調都調不動的時候，要先確認遊戲在獎勵什麼。**

### 動機

命中率、傷害、抗性都是**原因**；`player_strategy.md` 對安全關卡的定義量的是**結果**——
「能在平均 3 秒內殺死一個敵人」。原本三道閘門（裝備品質覆蓋率、卡關重試、以及
上面的詞條缺口）量的全是投入，而實測會脫節：一場全身史詩、沒死過、重試閘門也沒攔，
卻在關卡 150 之後每分鐘殺 0～1 隻，**整整 24 個在線小時零掉落零經驗**，三道閘門一道都沒響。

所以加了第四種目標度量 `ratePerMin`（計數器的滾動視窗差分）與兩個 `stageGate` 欄位：

```json
{ "id": "killRate", "kind": "ratePerMin",
  "counter": "panels.battle.lootStats.sources.field.kills",
  "windowSec": 300, "atLeast": 20 }
```
```json
"requireTargets": ["killRate"],
"targetRetreat": { "step": 5, "everySec": 300, "minStage": 1 }
```

`requireTargets` 裡有目標**已知**未達標時關掉自動推關，`targetRetreat` 再每
`everySec` 往回退 `step` 關，直到殺得動為止。`unknown`（視窗還沒攢滿）不算未達標。

門檻 20 隻/分不是憑感覺挑的——實測 100 小時的速率剖面：

| 關卡段 | 10–80 | 90–140 | 150+ |
| :--- | ---: | ---: | ---: |
| 中位速率（隻/分） | 21–31 | 3–13 | **0–1** |

### 第一輪實測：四種門檻全部輸給不設閘門

重度策略、100 小時牆鐘、4 個 seed：

| 變體 | 等級 最小/中位/最大 | 關卡 最小/中位/最大 | 擊殺 中位 | 死亡 中位 |
| :--- | ---: | ---: | ---: | ---: |
| 不設閘門 | 86 / **199** / **322** | 109 / **160.5** / **200** | 33,564 | 108 |
| ≥2 隻/分 | 86 / 174.5 / 279 | 100 / 136 / 150 | 35,992 | 102.5 |
| ≥5 隻/分 | 101 / 188 / 257 | 116 / 135 / 160 | 43,192 | 126 |
| ≥10 隻/分 | **147** / 194 / 256 | **131** / 145.5 / 150 | **49,268** | **74** |

門檻 20（指南建議值）單 seed 就崩了：Lv.322 → **Lv.85**、關卡 188 → 100，
而且**擊殺數翻倍**（26,928 → 54,467）。機制完全照設計運作，只是設計本身瞄錯了。

### 為什麼：離線結算不檢查「你打不打得動」

拿那一場跑完的存檔（Lv.322、關卡 188、命中 163.18、物攻 84,932）直接問遊戲。

**先排除一個嫌疑：數值曲線本身沒問題。**

| 關卡 | 血量 | 經驗 | 經驗 ÷ 血量 |
| ---: | ---: | ---: | ---: |
| 90 | ×1.0 | ×1.0 | ×1.00 |
| 130 | ×14.8 | ×12.2 | ×0.83 |
| 188 | ×626.3 | ×442.9 | **×0.71** |

血量與經驗幾乎同步成長，「每點傷害換到多少經驗」98 關只差 0.71 倍——
**線上收益本來應該與關卡深度幾乎無關**。

**那這一場為什麼打不動？因為裝備停止更新了。**

| 關卡 | 怪物閃避 | 有效命中率 | 線上收益（相對 90 關） |
| ---: | ---: | ---: | ---: |
| 90 | 56.2 | 100.0% | ×1.00 |
| 130 | 86.8 | 76.4% | ×0.63 |
| 188 | 141.0 | **22.2%** | **×0.16** |

這份存檔的面板命中卡在 163.18，關卡 188 的普通怪要 1,925 次命中才打得死，
實測每分鐘擊殺數 0～1。

⚠️ 當時我把這張表讀成「閃避曲線甩開了命中」，**那個歸因是錯的**——
修好離線之後同一份策略的四場實測，有效命中率在各自的刷關關卡全是 100%。
真正的因果是反過來的：漏洞讓 AI 停在原地掛機 → 裝備不再更新 → 命中才追不上。
詳見下面「那道命中牆也一起消失了」。

**而 `applyOfflineProgress`（js/save.js:941）這三件事一件都不看**：命中率、怪物血量、
你的傷害。它只做 `elapsed ÷ 20 秒 = 擊殺數`，再乘上 `offlineStageFor(G.stage.best)`
那一關的**菁英怪**（普通怪的 2 倍經驗）單殺價值。於是在關卡 188：

| | 每分鐘擊殺 | 對象 |
| :--- | ---: | :--- |
| 離線公式給的 | **3.0** | 菁英怪 |
| 線上實測做得到的 | **0.0 ～ 1.0** | 普通怪 |

| `stage.best` | 離線結算關卡 | 單殺經驗 | 16h 離線可升幾級 |
| ---: | ---: | ---: | ---: |
| 50 | 40 | 3,105 | 7.0 |
| 100 | 90 | 75,071 | 14.8 |
| 140 | 130 | 919,235 | 60.3 |
| 188 | 170 | 10,967,792 | **321.5** |
| 200 | 190 | 37,601,072 | **789.4** |

⚠️ 3 隻/分這個速率本身不算慷慨——`best=50` 時離線只有線上的 **0.2 倍**，前期它確實
比線上慢，正如直覺所料。**問題是它沒有被任何「打得動嗎」的檢查夾住**：關卡數一旦
跑贏傷害，這個固定費率就變成在發放角色根本做不到的擊殺。而它吃的是**歷史最高**
而不是當前關卡（`stageGo` 只改 `current`，`best` 是單向棘輪，js/combat.js:801），
所以退關也不會讓它縮水——推得深成了免費棘輪。班表下離線佔 2/3 的時間。

這就是產出閘門必輸的原因：退關省下的在線時間是線性收益，而它換掉的是一個
**與你的傷害脫鉤、隨關卡指數成長**的離線收入。

> **模擬器找到了一個設計沒打算給的最佳解**——「推到推不動為止然後掛機」。
> AI 停在關卡 188 一隻都殺不掉看起來很蠢，其實在那個公式下是對的。
> 策略層再怎麼調都贏不過這件事，因為它調的是行為，而問題出在報酬。

### 曾經試過的修法（已回退，量測結果保留）

做過一版「離線擊殺速率取線上實測值當下限」：野外擊殺時記錄實測速率，
離線結算取 `max(固定費率 20 秒, 實測間隔)`。它有效，但**引入了一個原設計沒有的概念**
（速率量測必然帶一個時間窗），最後決定不採用，改成把強度交給參數表。

保留下來的三個技術結論，日後若要重做請先讀：

| 邊界 | 不處理會怎樣 |
| :--- | :--- |
| 不能用「血量 ÷ 傷害」推算 | 漏掉技能、連擊、範圍攻擊，只算普攻會低估實際輸出約 **5 倍**，等於全面砍收益 |
| 暖機：分子分母要分開衰減 | 只維護「速率的移動平均」要一個時間常數才暖機完，開局 120 秒低估 5 倍 |
| 離線回來要重設時間錨點 | 否則回來打的第一隻怪會把整段離線時間算成「打不動」，之後再也領不到離線收益 |

### 第二輪實測：把誘因改掉之後，同樣的閘門變成最大的一筆改善

在**那個已回退的修正版本**上重跑同一組 seed（重度、100 小時、4 個 seed）。
這組數字現在的用途是回答一個假設性問題：**如果離線不再獎勵「掛在打不動的關卡」，
產出閘門值不值得開**——答案是非常值得。

| 變體 | 等級 最小/中位/最大 | 關卡 最小/中位/最大 | 擊殺 中位 | 死亡 中位 |
| :--- | ---: | ---: | ---: | ---: |
| 不設閘門 | 86 / 118 / 191 | 109 / 141.5 / 192 | 33,574 | 108 |
| ≥5 隻/分 | 101 / 188 / 257 | 116 / 135 / 160 | 43,192 | 126 |
| ≥10 隻/分 | 147 / 194 / 256 | 131 / 145.5 / 150 | 49,268 | 74 |
| **≥15 隻/分** | **196 / 299.5 / 343** | **150 / 150 / 160** | 52,356 | **41** |
| ≥20 隻/分 | 97 / 212 / 322 | 100 / 134.5 / 150 | 52,977 | 38.5 |
| ≥25 隻/分 | 52 / 53.5 / 74 | 42 / 46.5 / 87 | 51,899 | 56 |

- 不設閘門的中位等級從 199（漏洞版）掉到 118——**漏洞值大約 80 級**
- 掛上 15 隻/分之後中位等級 **299.5**，比漏洞版的 199 還高
- 門檻有明確最佳點：25 太嚴（鎖在關卡 42）、20 變異大、15 全面最佳
- 死亡數 108 → 41：AI 不再站在打不死的關卡硬撐

⚠️ 5 與 10 兩檔的數字在修正前後**完全相同**。那兩種設定本來就不會停在打不動的
關卡，速率上限自然從未生效——這正好反證修改只影響了它該影響的那一種情況。

> **這一節真正的教訓**：第一輪的結論「產出閘門沒用」是對的觀測、錯的歸因。
> 策略怎麼調都調不動的時候，要先確認遊戲有沒有在獎勵你不想要的行為。
> 模擬器最有價值的用途不是驗證策略，是**讓遊戲的誘因結構自己暴露出來**。

### 參數表旋鈕（`10-離線`）

離線模型的強度全部收斂到這幾格，程式不再寫死任何一個：

| 名稱 | 參數 | 預設 | 意思 |
| :--- | :--- | ---: | :--- |
| 有效離線時間 | a | 24 | 離線收益時數上限 |
| 擊殺速率 | a | 20 | 每 a 秒 1 隻（20 秒＝**每分鐘 3 隻**） |
| 計算等級 | a | 10 | 從歷史最高階段扣掉多少 |
| 計算等級 | **b** | 10 | 取整單位（扣減後捨去到 b 的倍數；設 1＝不取整） |
| 計算等級 | **c** | 1 | 關卡比例（先乘再扣減；設 0.5＝只算一半深度） |
| **怪物種類** | a | 1 | 1＝菁英（經驗與掉落倍率都較高）0＝普通 |

離線關卡 `= max(1, ⌊(歷史最高 × c − a) / b⌋ × b)`。預設值等於改動前的公式，
`tests/offline-stage-params.test.cjs` 有哨兵盯著這一點。

⚠️ **粗體那三格還沒進 Excel**。`config/CSV/game_parameters.csv` 是由
`config/Excel/game_parameters.xlsx` 產生的（`套用參數.bat` 第 2 步），直接改 CSV
下次轉檔就被蓋掉。程式已經支援，`apply_params` 會把還沒提供的格子列在
「參數表尚未提供」清單裡並沿用程式內的預設值——補上 Excel 欄位就自動生效。

### 那道「命中牆」也一起消失了——它本來就是漏洞的症狀

離線修好之前，關卡 188 的有效命中率只有 22.2%，看起來像是
`4-野外怪物／閃避率` 的成長曲線甩開了角色命中。修好之後回頭量四份存檔，
**四場的有效命中率在各自的刷關關卡都是 100%**：

| seed | 等級 | 刷關關卡 | 面板命中 | 怪物閃避 | 有效命中 | 身上命中詞條 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20260730 | 343 | 154 | 230.6 | 107.0 | **100%** | 2 條 |
| 20260731 | 196 | 145 | 220.5 | 98.8 | **100%** | 1 條 |
| 20260801 | 326 | 146 | 362.7 | 99.6 | **100%** | 3 條 |
| 20260802 | 273 | 135 | 210.9 | 90.8 | **100%** | 2 條 |

原因是命中率詞條的值是 `(基礎值 + 成長基礎值 × 每級 × (裝備等級−1)) × 品質倍率`，
**品質倍率才是主導項**：一條傳說 Lv100 的命中率詞條就是 **+29.8%**，神話 Lv150 是 **+50.5%**。
閃避每階只長 0.5～1.5。所以只要裝備跟得上，命中根本追得上——這幾套裝備
把剩下的詞條格全洗成命中率的話還能再加 950～1250%。

**先前那個 22.2% 是掛機造成的**：AI 停在關卡 188 不動，裝備從此不再更新
（面板命中卡在 163），於是看起來像數值曲線的問題。只要角色持續刷關，
裝備升級與缺口洗煉會一起把命中頂上去，`4-野外怪物／閃避率` 完全不必動。

⚠️ 這是**第三次**在同一件事上改歸因（先怪離線太強、再怪深度主導、再怪閃避曲線）。
前兩次錯在只看了症狀所在的那一份存檔。教訓是：**在行為已經扭曲的狀態下量到的任何
數值曲線問題，都要在行為恢復正常之後重量一次**——症狀會跟著消失，而在那之前
所有歸因都不可信。

### 只要角色在刷關，節奏就是正常的跑步機

在有持續刷關的那組實測裡，到 100 小時仍在往前推（60h 關卡 135 → 80h 145 → 100h 154），
物攻 372 → 176,368，沒有牆也沒有停滯。限制是一般的跑步機——怪物血量每階 ×1.06，
傷害得同步成長，後期大約每 20 牆鐘小時推進 10 關。
這是節奏設計問題，不是失衡；要調快就調 `4-野外怪物／生命` 的指數底，或加快裝備取得。

### 目前的設定與哨兵

**六份策略都沒有啟用產出閘門**——在現行的離線誘因下它實測會讓成績變差
（第一輪那張表）。機制、測試與哨兵都留著，要開只需在 `stageGate` 加：

```json
"requireTargets": ["killRate"],
"targetRetreat": { "step": 5, "everySec": 300, "minStage": 1 }
```

並宣告一個 `ratePerMin` 目標（counter 指向 `panels.battle.lootStats.sources.field.kills`）。
**若日後調整 `10-離線` 的參數讓線上刷關重新划算，記得回來重跑一次這個 A/B**——
第二輪那張表就是在那種前提下量的，門檻 15 隻/分全面最佳。

三支哨兵（`tests/policy-keys.test.cjs`）盯著這個機制最容易靜默失效的地方：
`requireTargets` 必須指到宣告過的目標、退關間隔不得短於取樣視窗、
計數器路徑必須在真實面板裡解得出來（實際開一場遊戲打到有擊殺再解一次）。

### 這個機制自己踩過的兩個坑

- **離線會偽造出「打不動」**。`state.gameTimeSec` 是含離線的牆鐘（`engine.gameTimeSec()`
  讀 `vNowMs`，而 `offlineFor` 會推它），但離線收益**不寫** `LOOT_STATS`。所以離線 16
  小時之後那一拍是「時間過了 57,600 秒、擊殺 0 隻」——速率被算成 0，每個離線日上線的
  頭五分鐘都會誤判成打不動並退關。中斷不是打不動，是沒在看：取樣間隔超過 `maxGapSec`
  就重新起算。
- **計數器要指到 `sources.field`**。`lootStats.kills` 的總數含塔戰 BOSS（js/tower.js），
  指到總數的話爬塔會被誤算成野外打得動。

## 裝等分段死鎖：AI 與真人差距的主因

### 症狀

極限策略、20 遊戲小時、10 個 seed：

| seed | 等級 | 最高關卡 | 停留關卡 | 物攻 |
| ---: | ---: | ---: | ---: | ---: |
| …070 | 54 | 50 | 42 | **334** |
| …072 | 56 | 50 | 42 | 582 |
| …076 | 54 | 50 | 42 | 245 |
| …078 | 50 | 50 | 42 | 503 |
| …079 | 51 | 50 | 41 | 448 |
| …071 | 80 | 100 | 90 | 7,708 |
| …075 | 88 | 100 | 82 | 21,810 |
| …077 | 55 | 100 | 100 | 3,368 |
| …073 | 65 | 119 | 119 | 10,260 |
| …074 | 134 | 141 | 140 | **34,983** |

**結果是雙峰的**：一半的 seed 卡在關卡 42 動不了 20 小時，另一半跨過關卡 50 之後
物攻差了兩個數量級。這不是運氣分佈，是兩個不同的穩態。

卡住那一組的最終存檔，13 個部位全部是「R4 史詩、**裝等 1**」，
而 299 件背包的 `maxLevel` 也是 1。物攻曲線在 7 小時之後**是往下走的**
（727 → 334）。

### 機制

三件事咬在一起：

1. `equipmentTierLevel`（`js/formula.js:1251`，`EQUIP_TIER_SIZE = 50`）：
   關卡 1~49 掉**裝等 1** 的裝備、50~99 掉裝等 50、100~149 掉裝等 100。
2. 詞條數值 `=（基礎值 + 成長基礎值 × 每級成長 × (裝等−1)）× 品質倍率`。實測 `atkFlat`：

   | | 裝等 1 | 裝等 50 | 裝等 100 |
   | :--- | ---: | ---: | ---: |
   | R4 史詩 | 12.0 | 335.4 | 665.4 |

   跨過關卡 50 是 **×27.95**；而同樣裝等 1 之下 R2 → R5 只有 7.0 → 16.0（**×2.29**）。
3. `stageGate` 的 `checkpoints` 把前期停在寫死的 `park` 區間，其中
   `maxStage: 50` 那一段是 **`[41, 45]`**——一個每一件掉落都是裝等 1 的區間。

於是形成閉環：

```
park [41,45] → 掉落永遠裝等 1 → 詞條只剩 base → 戰力上不去
  → 過不了關卡 50 守關 BOSS → 死了退關 → 品質覆蓋率閘門把它壓回 [41,45]
```

三道舊閘門（裝備品質覆蓋率、卡關重試、詞條缺口）一道都沒響，因為沒有一道在量
**「我停的地方掉得出比身上更好的裝備嗎」**。

### 為什麼換裝規則沒有救回來

舊的 `bestPerSlot` 用字典序 `[品質, 裝等, 太古數, 評分]`，**品質排第一**。
那等於用一個 ×2.3 的因子去否決一個 ×28 的因子：一件 R4 裝等 1 會把那個部位鎖死，
直到同品質的新裝等掉落為止。

原本的理由寫得很清楚也不算錯——「品質決定插槽數與附魔欄數，是換不回來的」。
問題是它被寫成了**否決權**而不是加分項。品質的價值（R4 三槽四詞條、R5 四槽五詞條）
在 `computeStats` 裡本來就算得到，不需要靠排在第一位來保護。

改成問遊戲「把它穿上去戰力是升是降」之後，插槽變少與強化歸零這兩件
`computeStats` 反映不了的成本，折算成一個**有界的門檻**（`socketPenalty` /
`upgradeGuard`），而不是否決。

### 這一節的教訓

> 「品質 > 等級 > 太古 > 評分」這條規則在 `player_strategy.md` 裡是對的——
> 它描述的是**真人心裡的排序**。翻譯成程式時被寫成字典序，於是一個
> 「通常成立的偏好」變成了「永遠成立的否決」。
>
> 策略文件寫的是傾向，程式寫的是規則。**把傾向翻譯成硬規則的那一步，
> 就是失真最常發生的地方**，而症狀永遠是「AI 卡住了」，不會是錯誤訊息。

## 邊際效益評估器：讓策略問得出「誰比較強」

### 為什麼需要第三層

策略層拿不到 `G`、`FIELD` 與任何遊戲函式，那是刻意的能力剝奪。代價是它**沒有辦法
評價任何東西**——它只能比較遊戲已經算好放進面板的數字。於是所有「哪個比較好」的
判斷都被迫寫成人工排序：詞條優先級清單、換裝的字典序、強化的品質上限表。

固定排序的問題不是排錯，是**這種形式表達不出正確答案**。實測本專案的面板：

| 詞條 | 邊際 ΔDPS |
| :--- | ---: |
| `atkFlat` | **+11.11%** |
| `hit` | +6.35% |
| `atkPct` | +2.96% |
| `critRate` | +1.90% |
| `critDmg` | **+0.52%** |

爆傷排最後，因為那一刻的暴擊率只有 5%——同一張表在暴擊率 60% 時會完全倒過來。

`scripts/sim/evaluator.js` 是這一層。它跑在**引擎的** vm context（看得到 `G`、
`FIELD` 與全部遊戲函式），把結果算成純資料經 `panels.eval` 交給策略沙箱。
策略仍然只做一件事：在一堆數字裡挑最大的。

```
run_sim.js ──決策點──▶ engine.panel('eval')
                          │  evaluator.js（引擎 context：有 G / FIELD）
                          │    computeStats(假設裝備) → 遊戲算的 ΔDPS / ΔEHP
                          ▼
                       純資料 ──▶ policy.decide(深拷貝) ──▶ 指令
                                    策略 context：仍然沒有 G / FIELD
```

三個沒有被放寬的地方：

| | 為什麼 |
| :--- | :--- |
| 隔離 | 策略拿到的仍然只是深拷貝的純資料，`test_policy_isolation.js` 12 項反證不受影響 |
| 沒有第二份公式 | 每一處算式都只由遊戲函式串接（`computeStats` / `defReduction` / `affixBaseValue`…） |
| 不出貨給玩家 | 放在 `scripts/sim/`，不是 `js/worker/`——這東西只有 AI 模擬器用得到 |

### 它算什麼

| 欄位 | 內容 |
| :--- | :--- |
| `combat` | `timeToKill` / `timeToDie` / `cause`（`DPS_TIMEOUT` 或 `EHP_TOO_LOW`）|
| `affixRoi` | 每條詞條多一條值多少 ΔDPS%／ΔEHP%（合成一件裝備再問 `computeStats`）|
| `equippedAffixes` | 身上每條詞條拿掉會掉多少——洗煉時「犧牲哪一格」的依據 |
| `slotUpgrades` | 每個部位換上背包最佳候選的真實戰力差 |
| `tier` | 裝等分段斷點與跨過去的增幅 |
| `resources` | 以遊戲當下報的成本為分母的資源水位 |

### 兩個必須一起講的限制

**1. DPS 模型只含普攻，低估約 5 倍。** 這對 ROI 無害（ROI 是比值，常數倍率會約掉），
但絕對時間會全錯。所以 `timeToKill` 一律先用遊戲自己的 `currentDps()`（最近 10 秒
實際傷害）校正模型尺度：模型負責「對屬性的敏感度」，遊戲負責「絕對值」。
`currentDps()` 還沒量到時回 `unknown`，**不猜**。

**2. 兩個係數是抄的。** 命中夾值（5%～100%）與探針強度取樣點在遊戲裡是內嵌在
`resolveHit` 的字面值，沒有具名函式可呼叫。`tests/sim-evaluator.test.cjs` 直接
比對 `resolveHit` 的原始碼當哨兵，而且 `run_summary.json` 的 `evaluator.model`
每一場都會揭露。

### 唯讀性是這裡最容易破的一件事

評估器要問「假如換上這件會怎樣」，用的是 `computeStats(override)`。踩過一次：
`itemScore()` 內部的 `itemEnchants()` 會把 `{ enchant: null }` **就地**正規化成
`{ enchants: [] }`——於是「看一下背包」這個純讀取動作改掉了存檔，
同 seed 的兩場雜湊不同，而症狀只是一串對不上的字串，完全看不出來是誰動的。

所以任何流進遊戲函式的背包物品一律先過 `evalSafeItem()` 複製。
`tests/sim-evaluator.test.cjs` 以「跑過評估器與沒跑過，存檔逐位元組相同」反證這件事。

### 效能：這個機制能不能開著跑，取決於這一節

| 版本 | 每次面板 |
| :--- | ---: |
| 初版 | 74 ms |
| `itemScore` 改成整份背包預先算一次（不要寫在 sort 的比較函式裡） | 30 ms |
| 詞條 ROI 先選宿主再精算一次（原本每個合法部位各精算一次） | 20 ms |
| 身上詞條只探 ROI 前三名的宿主部位（原本全身 13 個） | 13 ms |
| 規劃結果快取 `refreshSec` 遊戲秒（以 `GT` 為鍵，不是真實時間） | **6.7 ms** |

決策每 5 秒、20 遊戲小時＝ 14,400 次，最後的版本替一場 11 分鐘的模擬多加約 100 秒。

⚠️ **完整的 `panels.eval` 絕對不能排進 1Hz 觀測**。敗因診斷必須在死亡瞬間附近取樣，
所以另外有一個便宜的 `panels.evalCombat`（只做戰鬥側寫，不碰 `computeStats`，
0.02 ms）。`policy.profile.combat` 宣告成陣列時**只有第一條**會被加進觀測面板，
`tests/sim-evaluator.test.cjs` 有哨兵盯著 `eval` 沒有混進去。

### 第一版實測踩到的兩個坑（都已修，都不會有錯誤訊息）

第一版跑完 6 個 seed 之後有兩個 seed **退步**（最高關卡 100 → 51），
而它們的物攻反而變高（8,409 → 12,282）。「變強但推得更慢」這個組合正好指出兩件事：

**1. 進了安全區間就原地不動。** 舊的 `park` 語意是「低於下緣才往前推」，
對寫死的小區間（`[11,15]`）沒問題；但裝等分段把上緣拉到 99 之後，
原地不動就變成停在 51 整整六小時，而對照組同時間已經推到 89。
分段之內往前推是純賺——裝等不變，但關卡愈深品質擲骰愈好。
現在 `tierBand` 模式下目標是推到**上緣**。

**2. 資源門檻用了「最貴那件」當全體分母。** 金幣被寶石商店吃掉之後最貴那件變成
付不起，而整條強化規則是拿那一個數字當總開關——**一個部位付不起，全身十三個
部位一起停工**。實測那一場跑到第 20 小時握著 **157,034 碎片沒有用掉**。
改成逐部位判定：付得起的就投，付不起的略過那一格。

> 兩個坑是同一種形狀：**把一個局部的限制寫成了全體的開關**。
> 這類錯誤在報表上永遠看起來像「AI 很保守」，不會像 bug。

### 第三個坑：整段裝等分段被無條件放行（獨立驗證抓到的）

前兩個坑是自己找到的，這一個不是——是 Codex 拿**沒有被挑選過**的 8 個 seed
重跑 A/B 抓到的（`docs/ROI_AGENT_VERIFICATION_2026-08-03.md`）。
7 個 seed 大幅改善，但 seed `20260903` 崩掉：

| | 等級 | 最高關卡 | 物攻 | **死亡** |
| :--- | ---: | ---: | ---: | ---: |
| 舊策略 | 86 | 100 | 4,653 | **33** |
| ROI 第一版 | 57 | 50 | 477 | **1,126** |

死亡數是關鍵：20 小時死 1,126 次，平均每 64 秒一次。角色被推到分段深處反覆送死，
撿不到裝備、也跨不過裝等斷點——**這個機制擋掉了它自己要促成的那件事**。

原因在 `tierPush` 的這一句：

```js
if (!behind && gain >= minGain) passGate = true;   // ← 沒有任何存活條件
```

`behind` 的定義是「身上裝等落後於當前分段能掉的」。但在**第一個分段**（關卡 1~49）
裡，掉落的裝等恆為 1，身上的自然也是 1，所以 `behind` 永遠是 false——
整段被無條件放行，一路推到分段底。三道舊閘門加上新的裝等閘門，
**沒有一道在問「你打得動嗎」**。

修法是新增上限型目標（`atMost`，原本只有 `atLeast`）：

```json
{ "id": "deathRate", "kind": "ratePerMin",
  "counter": "panels.battle.lootStats.sources.field.deaths",
  "windowSec": 600, "atMost": 0.5 }
```
```json
"tierPush": { "advanceRequiresTargets": ["deathRate"] }
```

只擋**前進**，不強迫後退——後退交給遊戲自己的死亡退關與 park 下緣，
這一層的退關來源已經有兩個，再加一個只會讓歸因變難。

> 第一次修在錯的地方：只把條件加在「分段之內往前走」那條路徑上，
> 而實際失控的是「放行推關」那一條。測出來完全沒有效果。
> **兩條前進路徑都要管**——這件事只有把測試寫成「餵一個超標的死亡率進去，
> 看閘門會不會關」才驗得出來，讀程式碼讀不出來。

### 門檻與快取間隔的實測掃描（8 seed × 20 小時，同一組 seed）

| 版本 | 等級 最小/中位 | 關卡 最小/中位 | 物攻 最小/中位 | 縮時 |
| :--- | ---: | ---: | ---: | ---: |
| 舊策略 | 54 / **80.5** | 50 / **100** | 302 / **6,511** | 296x |
| 無死亡閘門 | 57 / **132.5** | 50 / **148** | 477 / **36,966** | 165x |
| **死亡率 ≤0.5、refresh 15s** | **116 / 158** | **136 / 150** | **39,960 / 59,753** | **187x** |
| 死亡率 ≤0.8、refresh 15s | 112 / 172.5 | 130 / 150 | 16,032 / 66,474 | 134x |
| 死亡率 ≤0.8、refresh 45s | 51 / 137.5 | 50 / 142.5 | 346 / 48,735 | 222x |

兩個可以直接讀出來的結論：

- **0.8 的中位比 0.5 高，但下緣掉了 2.5 倍**。這次改造要修的就是下緣崩掉的失效模式，
  所以取下緣，選 0.5。
- **`refreshSec` 從 15 拉到 45 會讓整個下緣崩回原點**（物攻最小值 39,960 → 346、
  關卡最小值 136 → 50），換到的只有縮時 187x → 222x。規劃太舊比算得慢更貴。

### 效能：那道 70% 的門檻是錯的門檻

驗證任務裡訂了「ROI 的縮時倍率不得低於舊策略的 70%」，實際是 **63%**。

實測評估器在真實深度狀態（Lv.221／關卡 150／背包 303 件）的成本：

| | 每決策點 |
| :--- | ---: |
| 只跑模擬 | 6.74 ms |

評估器確實佔了七成——而且**不是因為跑得比較深**：舊策略自己在關卡 50 到 140 之間
縮時倍率一直是 257~332x，深度本身不影響。

但唯一達到 70% 的設定（refresh 45s）**把改造要修的失效模式整個放了回來**。
達標會是自欺，所以維持 63% 並在這裡揭露。要再快就得從
「整份背包每次重算 `itemScore`」下手（快取 id→分數），那是還沒做的事。

## 分段地板變成吸收態：關卡 100 與 150 的死鎖

### 症狀

`sim_ab_forge` 那批 8 個 seed，**7 個在第 5~18 小時停止產出**，之後直到跑完
（最久 10 小時）都在原地。三批的對照：

| | 20 小時內全程有產出的 seed |
| :--- | ---: |
| `sim_ab_fix2`（基準） | 5 / 8 |
| `sim_ab_forge`（加熔爐零件） | **1 / 8** |
| `sim_ab_wall`（本節修正後） | **8 / 8** |

停下來的位置全部是 **關卡 150 或 100**——`EQUIP_TIER_SIZE`（50）的倍數，
也就是裝等分段邊界。這不是巧合。

### 機制

退關的地板取「當前裝等分段的底」，防的是跌破分段、掉落裝等退一階：

```js
if (tierFloor !== null && tierFloor > floorStage) floorStage = tierFloor;
...
if (gStage > floorStage && 冷卻到了) { 送出退關 }
```

角色推關時一定會踩上分段邊界。踩上去的那一刻 `gStage === tierFloor`，
於是 `gStage > floorStage` **恆為 false**，退關指令再也送不出去。
進得去、出不來——一個吸收態。

實測 `sim_ab_forge` seed20260908：第 10 小時踏上關卡 150，之後 10 小時
`stage.go` 整場只送了 22 次（全被地板吃掉），累計擊殺從 7,047 爬到 7,103，
**10 小時 56 隻**。

而那一關的數字是：

| | 值 |
| :--- | ---: |
| 怪物血量（關卡 150） | 14,268,860 |
| 怪物防禦 | 454,009 |
| 角色物攻 | 33,797 |
| 角色實際輸出 | ≈ 25K/秒 |
| **一隻怪要打** | **9.5 分鐘** |

角色**一次都沒死**。牠們不是打不過，是打不完。

> ⚠️ 這段程式碼原本的註解寫著「地板來自靜態分段邊界，不會因為記錯而漂移，
> 所以它不會造成死鎖」。前半對，結論錯——不需要漂移就能死鎖，
> 只要**站在地板上**就夠了。

### 兩項修正

**1. 地板只在分段之內生效**

```js
if (tierFloor !== null && tierFloor > floorStage && gStage > tierFloor) floorStage = tierFloor;
```

站在分段底時這道地板已經沒有東西可以保護：底下那一段本來就更差，
但「更差的掉落」遠好過「每小時 5.6 隻」。分段**之內**的退關仍然擋著。

**2. `tierPush` 的前進條件加上 `killRate`**

```json
"advanceRequiresTargets": ["deathRate", "killRate"]
```

原本只看死亡率。但這裡的失敗模式是 **DPS_TIMEOUT 而不是 EHP_TOO_LOW**——
角色完全不死，死亡率一路達標，於是閘門繼續放行往更深處推。
**「我沒死」不能當成「我推得動」的代理指標**，這正是敗因側寫要把兩者分開的理由。

### 實測（8 seed × 20 小時，同一組 seed）

| 指標（最小/**中位**/最大） | `sim_ab_fix2` | `sim_ab_wall` |
| :--- | ---: | ---: |
| 等級 | 116/**158**/245 | 259/**380**/1,000 |
| 最高關卡 | 136/**150**/170 | 180/**213**/280 |
| 物攻 | 39,960/**59,753**/94,032 | 151,658/**314,577**/626,618 |
| 死亡 | 294/**405**/452 | 52/**83**/157 |
| 洗煉成功 | 308/**331**/454 | 980/**1,412**/1,779 |
| 擊殺 | 17,531/**23,176**/27,326 | 9,535/**13,005**/18,170 |

擊殺數下降 44% 不是退步：關卡深了，一隻怪的經驗與掉落大得多，
等級中位數 158 → 380 就是證據。**用擊殺數當產出指標會在這裡誤導**。

> 這一節的教訓與「裝等分段死鎖」那一節是同一個：
> 任何「不得低於 X」的地板，都要問「站在 X 上的時候會發生什麼」。
> 邊界值不是邊角案例——角色一定會走到那裡並停下。

## 熔爐零件：唯一能把材料上限本身推高的槓桿

改造前實測 20 小時的存檔，兩座熔爐都是 **0/3 格、一個零件都沒裝**，
而零件庫存裡每一種都已經是 T7×10（`PART_KEEP_PER_KEY` 上限）。
整個系統從來沒被策略碰過。

零件是**快照制**（`newforge.js newForgeInstallPart`）：安裝時複製「玩家持有的
該類型最高階」的數值，**不佔用也不消耗庫存**，同類型可以重複裝滿、
兩座爐可以共用同一批零件。唯一的上限是零件格數（每爐 3~8，金幣逐格解鎖）。

因此 T7 精粹透鏡裝滿 8 格 ＝ 該爐分解時附魔精華產出率 **+1120%（×12.2）**。
精華是這份策略的硬上限（改造前單場取得約 1,535 點、洗一次 5~6 點、結局存量 8），
這是唯一能把上限本身推高的槓桿，而不是在同一塊餅裡重新分配。

### 三個訊號，全部由遊戲的面板提供

| 訊號 | 資料來源 | 行為 |
| :--- | :--- | :--- |
| 基本盤 | `plan[爐序]` | 一爐精粹透鏡、一爐碎片熔煉爐 |
| 微調 | `view.essence` / `view.scrap` 的**滿足率** | 較緊的那一種多拿 2 格 |
| 加速 | 該爐 `queue.length + belt.length` | 塞車才換上加速齒輪 |

**⚠️ 微調不能用「庫存低於某個絕對值」。** 這份策略把精華與碎片都花到見底
（結局：精華 8、碎片 661），任何絕對門檻都會同時成立，規則等於整場不動。
改比 `庫存 / ref` 的滿足率——`ref` 是策略宣告的「存到多少算寬裕」，
作用是把兩種單位換算到同一把尺。

**⚠️ 也不能用 `ref / 庫存`。** 那在庫存 0 時會退化成「`ref` 比較大的那一種永遠贏」，
開局兩種都是 0 卻會判成碎片緊 100 倍。滿足率沒有這個問題：0/50 與 0/5000 都是 0，
分不出來就不動。

**⚠️ 判斷要有遲滯。** 兩種材料都是「攢一批、一次花光」，庫存訊號本身在跳。
第一版沒有遲滯，實測 seed20260903 的日誌：16:50 把碎片熔煉爐裝進 1 號爐、
16:55 又換回精粹透鏡，整場 308 次安裝／146 次拆卸，大半是這樣來回翻。
現在要同一判斷連續成立 3 次（＝15 分鐘）才動手。

### 一個容易誤解的事實：兩座爐怎麼分配其實不重要

熔爐派工取**負載最少**的那一座（`newForgeDispatchTarget`），裝備平均分到各爐。
所以「#1 八透鏡 ＋ #2 八碎片」與「#1 六透鏡二碎片 ＋ #2 六碎片二透鏡」的
**總加成完全相等**：(1120+0)/2 = (840+280)/2 = 560。

真正的槓桿是**全部 16 格裡各類型佔幾格**，不是哪一格在哪一座爐。
「一定要開 2 座爐、每座 8 格」抓到的正是這一點——重點在 16 這個總格數。

### 實測（機制層面）

| 熔爐指標 | 改造前 | 改造後 |
| :--- | ---: | ---: |
| 零件格合計 | 6 | **16** |
| 已裝零件 | **0** | **16** |
| 精華產出加成（中位） | 0% | **+1,400%** |
| 碎片產出加成（中位） | 0% | **+840%** |
| 洗煉成功次數（中位） | 331 | **1,412** |

8 個 seed 全部在遊戲時間 2 小時內把兩座爐推到 8/8（每爐 18 萬金），
之後隨零件階級上升持續重裝到 T7——快照制不會自己升階，不重裝就會用早期的
低階數值跑完整場。

> ⚠️ `newForgeUninstallPart` 是 `splice`。同一拍要拆多個零件時**必須由大到小送**，
> 否則先拆小索引會讓後面每一個索引往前位移一格，拆錯零件而且不會報錯。
> （`tests/sim-forge-parts.test.cjs` 有哨兵。）

## 附魔書單：一本書在結構上填不滿兩格

實測 20 小時的存檔，武器／手套／護腕／雙戒**五個攻擊部位全部停在 1/2 格**，
而背包裡躺著 `fire×44 lightning×45 dark×41 poison×30 light×28`，
策略宣告的 `atk` 書單只有 `['ice']`，而 ice 只剩 9 本。

關鍵不是「清單太窄」而已——**同一件裝備不能重複附同一種書**
（遊戲回「已有同類附魔且數值不會提升」）。所以單一本書的清單
**在結構上就填不滿第二格**，跟手上有幾本 ice 完全無關。
這件事讀策略資料看不出來，要把存檔攤開對照 `enchantCapFor` 才會發現。

附魔只花 1 點精華（`ENCHANT_ESSENCE_COST`），是整份策略最便宜的戰力來源。

### 補書單 vs 分散元素是兩個問題，必須分開問

第一版一次改了四件事（三個書單、`spread` 加入 `atk`、`maxPerDecision` 4→6），
結果變差，而那正是「歸因不出來」的典型陷阱。拆開之後：

| 8 seed × 20 小時 | 最高關卡 最小/**中位**/最大 | 平均 |
| :--- | ---: | ---: |
| `sim_ab_wall`（原本，`atk: ['ice']`） | 180/**212.5**/280 | 223 |
| `sim_ab_ench`（補書單 ＋ atk 輪流取用） | 183/**199.5**/264 | 210 |
| **`sim_ab_ench2`（補書單，不輪流取用）** | **188/251/280** | **240** |

`ench` 對 `ench2` 的配對比較（書單相同，只差 `spread`）：**`ench2` 勝 6/8**。
所以拖累的是 `spread` 把六種元素分散到不同裝備上，稀釋了主力元素——
`player_strategy.md` 的原意本來就是攻擊格集中在冰凍。

### ⚠️ 註記字串不能寫在 `byCategory` 裡

`byCategory` 底下的每一個值都會被當成書單走訪，
註記字串會被**逐字元拆成書鍵**。這個錯犯過兩次，
第二次是 `tests/policy-keys.test.cjs` 擋下來的（訊息是「引用了不存在的附魔書『i』」）。
註記一律放在 `byCategory` 之外。

### 這一節真正的教訓：8 個 seed 的解析度

`wall` 對 `ench2` 的配對是 **4 勝 4 敗**，中位數卻差 18%——
因為勝的四個贏很多（+160%~+250%）、敗的四個輸得中等。
單一 seed 的等級落差橫跨 257~1000，**8 個 seed 大約只分辨得出 ±40% 以上的效果**。

所以這一項的取捨不是靠中位數決定的，是靠**結構論證**：
一本書填不滿兩格是確定的事實，補齊之後在所有彙總統計上不輸，那就留著。
±20% 這個量級要 16~24 個 seed 才有機會定案——
在那之前把「中位數變好了」寫成結論，就是上一輪犯過的錯。

> 另外：等級在 **1000 封頂**（`sim_ab_ench2` 有兩個 seed 剛好停在 1000）。
> 封頂之後等級就不再是有效的比較指標，改看**最高關卡**（沒有上限）。

## 太古詞條：查清楚了，但兩條路都不通（負面結果，保留紀錄）

「太古詞條過少」是兩件事，分開查完的結論是**兩條都不值得做**。
這一節記的是負面結果——不記的話下一個人會再走一次同樣的路。

### 數量：唯一的輸入是幸運值，而幸運值堆不起來

掉落裝備的太古條數由 `rollAncientAffixCount(affixCount, luck)` 決定，
`luck`（幸運值）是唯一輸入。實測三個 20 小時存檔的 `luck` 全部是 **0**。

能堆到多少：

| 來源 | 可得幸運值 |
| :--- | ---: |
| 頭盔／雙戒／項鍊各一條 `luck` 詞條（含強化倍率） | ≈ 1,100 |
| 全部 53 個插槽塞滿 5 級太陽石 | ≈ 716 |

換算成效果（5 詞條裝備的期望太古條數）：

| luck | 期望條數 | 相對 luck 0 |
| ---: | ---: | ---: |
| 0 | 0.350 | — |
| 1,000 | 0.399 | +14% |
| 4,000 | 0.479 | +37% |

**花 4 個詞條格換 +14%，而且只對未來的掉落有效**——那些裝備遲早又被換掉。
全身插滿太陽石換 716 點更是明顯虧本。所以不做。

> 順帶：`js/item.js` 的註解「幸運值（洗煉數值取優）」是錯的。
> `luck` 全專案只被 `rollAncientAffixCount` 用到，洗煉的數值只受 `affixCap` 影響。

### 品質：機制正確、估值也修對了，但實測輸

遊戲規則（`js/item.js rerollSingleAffix`）：**太古與否只看位置**——
太古位置洗煉只換詞條種類、永遠維持太古，而太古的數值走另一條乘算路徑：

```
一般  baseV × strengthMult(roll)          探針(roll 取中點) = ×1.00，滿值 = ×1.20
太古  baseV × AFFIX_MAX_VALUE_MULT × ANCIENT_AFFIX_VALUE_MULT = ×1.62
```

所以洗太古位置是同樣成本、保證滿值。而實測 8 個存檔的 47 個太古位置有 **49%**
放著遊戲權重 ≤ 1 的詞條（生命值 0.05、法力值 0.075、生命恢復 0.6 這一類）——
一批「保證滿值」的格子被閒置。

做的三件事都驗證過：評估器多給一組太古估值（倍率由 `computeStats` 算出來，
實測正好 1.620）、ROI 規則改成挑「淨收益最大」而非「損失最小」、只在
`reroll-by-roi` 放行。**但 8 seed × 20 小時的配對結果是等級 1/8 勝、關卡 3/8 勝**
（中位等級 688 → 446）。

原因：**ROI 的收益是「如果洗出第一名那條」的最佳值，而洗煉是從詞條池隨機擲的。**
這個樂觀在舊版就存在，門檻剛好擋得住；乘上 1.62 之後就擋不住了，
於是精華被耗在反覆重擲太古位置上（精華結局存量 1,682 → 272）。

要重啟這一項，得先把 ROI 的收益改成**池的期望值**而不是最佳值。
評估器的太古估值、`ancientProbeTop` 旋鈕與四支測試都留著，
改好之後把 `keepAncient` 設回 `false`、`ancientProbeTop` 開回 4 即可。
目前 `ancientProbeTop: 0`，面板成本回到 81ms（開 4 是 87ms、17 條全開是 98ms）。

## 觀測與行動是兩種節奏

| 參數 | 意義 | 是否隨玩家強度變化 |
| :--- | :--- | :--- |
| `decideEveryGameSec` | 玩家多久做一次後勤（換裝、洗詞條、鑲寶石…） | 是（輕度 60s ～ 極限 5s） |
| `observeEverySec` | 玩家多仔細看戰鬥 | **否**，預設一律 1 秒 |

> 這兩件事原本是同一個旋鈕。後果是玩得少的人連戰鬥觀測都變粗——而卡關重試間隔正是
> 「觀察到的敵人殘血百分比當分鐘數」（`retryAt = now + max(10, minHpPct) × 60`），
> 於是低強度玩家被**系統性地多罰一次**。真人盯著螢幕看到的戰鬥細節，
> 不會因為他今天只上線兩小時就變粗。

實測（seed=4242，3 遊戲小時，全程不送指令，所以遊戲演進完全相同，差異純粹來自觀測）：

| 取樣間隔 | 偵測到的失敗次數 | 平均推導重試間隔 |
| :--- | ---: | ---: |
| 1s（接近真人） | **61** | 39.1 分 |
| 15s（重度） | 31 | 40.5 分 |
| 60s（輕度） | **33** | **64.0 分** |

兩個效果疊在一起：60 秒取樣**漏掉近一半的失敗**（整場交戰落在兩次取樣之間，
那一關根本沒被記成卡點，針對性強化與重試閘門完全不會啟動），看到的殘血還偏高，
重試間隔被拉長 1.6 倍。

`--observe-every=N` 可覆蓋；設成與 `decideEveryGameSec` 相同即還原拆分前的行為
（實測輕度玩家 `--observe-every=60` 精確重現舊雜湊）。

實作上，觀測走 `policy.observe(state)` 這個獨立進入點，隔離方式與 `decide` 完全相同，
且只建 `observePanels`（從 `track.monster` / `track.stage` 與速率目標的 `counter` 推導）
——**不含背包面板**，否則 1Hz 觀測會變成每秒建一次背包，那是這個設計最容易踩的效能陷阱。

## 線上／離線班表

策略以 `dailyActiveHours` 宣告每日遊玩時數，驅動端據此在**在線模擬**與**離線結算**
之間切換。每個 24 小時週期先連續在線該時數，其餘時間離線。

> 在 2026-08-01 之前這個欄位是死的：四份強度策略都宣告了，但 `createPolicy()` 沒有
> 把它轉出來、`run_sim.js` 也沒有讀。四種強度全部被當成 24 小時不間斷在線，
> 只有決策頻率不同——輕度玩家被模擬成一個永不睡覺、每 60 秒操作一次的人。

**⚠️ 啟用班表後 `--hours` 是牆鐘時間（含離線）**，不是線上時數。
`run_summary.json` 的 `schedule.onlineHours` 才是實際跑了模擬的時數，兩者不可混用。

`--ignore-schedule` 忽略宣告值、全程在線，用來重現班表實作前的行為。

### 離線與線上是完全不同的兩套模型

離線收益一律由遊戲的 `applyOfflineProgress`（`js/save.js`）計算，harness 不碰任何公式。
它是**固定費率**的，與角色實際 DPS 無關：

| 常數（`js/formula.js`） | 值 | 意義 |
| :--- | :--- | :--- |
| `OFFLINE_KILL_INTERVAL` | 20 秒 | 每 20 秒殺 1 隻菁英怪 |
| `offlineStageFor(best)` | `⌊(best−10)/10⌋×10` | 打的是比最高關卡低 10~19 關的菁英 |
| `OFFLINE_MAX_HOURS` | 24 | 收益上限；未滿 1 分鐘不計 |

`sim/engine.js` 的 `offlineFor(sec)` 照真實流程走：`stampSavedAt()`（等同關掉遊戲時
的落地）→ 推進虛擬時鐘但不跑 `simStep` → 呼叫 `applyOfflineProgress()` 的同步路徑。

### 實測：班表讓四種強度終於分得開

48 小時牆鐘、seed=777、全新角色：

| 強度 | 每日在線 | 實際在線 | 最終等級 | 最高關卡 |
| :--- | ---: | ---: | ---: | ---: |
| 輕度 | 2h | 4h | Lv.48 | 50 |
| 中度 | 4h | 8h | Lv.50 | 50 |
| 重度 | 8h | 16h | Lv.56 | 50 |
| 極限 | 24h | 48h | Lv.64 | 115 |

同一份輕度策略若用 `--ignore-schedule`（＝班表實作前的行為）會跑到 **Lv.76 / 關卡 70**，
比實際高出 28 級。**先前所有輕度與中度的模擬數據都要重跑。**

兩個值得注意的現象，都是這張表第一次看得到的：

1. **輕度與中度幾乎沒差**（Lv.48 vs Lv.50）。離線收益是線性費率且遠未達 24 小時上限，
   輕度玩家離線更久、離線收益反而更多（7,920 vs 7,200 隻），把在線時數的差距抵銷掉了。
2. **前三種強度全部卡在關卡 50**，只有極限玩家過得去。那正是
   `player_strategy.md` 寫的 50 級守關 BOSS。

## 真人基準線：錄一場真人的，拿去跟 AI 的相減

### 為什麼需要這個

「AI 跑起來跟真人有落差」在這條管線出現之前是一句沒辦法追下去的話——只有 AI 那條
曲線有數字，真人那條沒有。要調策略、要判斷 `player_strategy.md` 哪一段翻譯失真，
都得先有真人那條線。

### 三個步驟

**1. 錄**　起伺服器（`啟動數值模擬器.bat` 或直接跑 `node tools/sim_server.cjs`，
它本來就有靜態託管），以決定論模式開遊戲，正常玩：

```
http://127.0.0.1:28342/index.html?seed=777&record=1
```

必須走 `http://127.0.0.1`，不能用 `file://`——錄製器與決定論模式都只認本機 hostname。

右下角會出現「● 錄製中」的徽章，顯示已錄到幾道指令、幾筆樣本。玩完按「匯出軌跡」
下載 JSON。可選 `&rowEvery=N` 調整樣本密度（預設每 10 則 tick 一筆）。

錄到的東西有三樣：起始存檔、指令軌跡（含**執行當下**的 `simT`）、實測 view 樣本。

**2. 驗**　證明軌跡是完整的——漏一道指令不會有任何錯誤訊息：

```bash
node scripts/verify_trace.js human_trace_seed777_....json
```

它用同一份存檔、同一個 seed 重播軌跡，再與錄製當下的實測樣本逐檢查點比對。
PASS 同時證明了三件事：軌跡沒漏指令、時間戳精確到步、headless 忠實於瀏覽器。
做這一步建議用 `&rowEvery=1` 錄一段短的（幾分鐘），檢查點最密。

**3. 比**　把真人那一場跑成標準輸出，再與 AI 的相減：

```bash
node scripts/run_sim.js --trace=human_trace_seed777_....json --out=sim_out_human
node scripts/run_sim.js --policy=scripts/sim/policy.moderate.json --seed=777 --hours=3 --out=sim_out_ai
node scripts/compare_runs.js sim_out_human sim_out_ai
```

`--trace` 走的是同一支 `run_sim.js`、同一組快照欄位、同一份 `run_summary.json` 格式，
所以兩邊的輸出天生可以相減。這也是軌跡重播刻意不另寫回放腳本的原因——第二套報表
遲早會跟第一套長歪，而長歪的那一刻沒有人會發現。

### 精確的時間戳是怎麼拿到的

指令是非同步的，主執行緒自己蓋的時間戳一定是糊的，而糊掉的軌跡重播出來會是另一場
（亂數序列錯開一步，之後每一次掉落都不同）。

關鍵在 `js/worker/sim.worker.js` 的 `MSG_IN.CMD` 分支：指令成功後 Worker 會**立刻補送
一則 tick**。Worker 的 `onmessage` 是同步的，ACK 與那則 tick 之間插不進任何東西，
所以「ACK 之後收到的第一則 tick」的 `view.simT` 就是指令執行當下的模擬時鐘，精確到步。

因此錄製器不需要自己算時間——精確的時間本來就在訊息流裡。
（唯一需要協議配合的是 `simT` 這個欄位本身，見 v14；`gt` 在戰鬥暫停時會停住，
當不了對齊軸。）

| 檔案 | 角色 |
| :--- | :--- |
| `js/recorder.js` | 錄製器本體。只在本機 `?record=1` 時做事，正式遊玩是空殼 |
| `js/bridge.js` | 兩個鉤子：`send()`（操作的唯一出口）與 `start()`（起始存檔） |
| `scripts/sim/trace.js` | 把軌跡包成與 `sim/policy.js` 相同的決策來源介面 |
| `scripts/sim/viewdiff.js` | `cross_check` 與 `verify_trace` 共用的比對判定 |

### 已知限制（不要在報告裡略過）

- **協議 v14 之前錄的檔**只能退回以 `gt` 對齊，而 `gt` 在戰鬥暫停時會停住，
  那種錄製只要暫停過就重播不出來（`run_summary.json` 的 `trace.axis` 會是 `gt`，
  `verify_trace.js` 會在比對前先警告）。用目前版本重錄即可，v14 起以 `simT` 對齊，
  暫停已經不是限制——實測：暫停 2 次共 89 個 tick、`gt` 與 `simT` 差 17 秒，
  332 個檢查點仍然完全一致。
- **同一個 tick 內連送的多道指令**會共用同一個刻度（一步 0.1 秒，人手連點兩下必定同步），
  但那一種重播會在同一步依序送出、完整重現，**不是問題**。
- **錄製不會動到你的存檔**（2026-08-01 起）。決定論模式下 `requestPersist` 會擋掉所有
  非自願的落地（`auto` / `folder` / `shutdown`），只有明確按下手動存檔或重新開局才會寫。
  在此之前 `onVisibility` 的 `SHUTDOWN` 沒有被擋，錄製期間切一次分頁就會蓋掉
  `auto_current`——如果你用的是舊版本，錄製前請先備份。
- **軌跡重播每步都問一次決策**（`decideEveryGameSec` = 一步），所以 `engine.view()`
  的呼叫次數是一般策略跑的一百多倍。它會順帶呼叫 `updateShownRes()`，讓重播存檔的
  `shownRes` 旗標比瀏覽器那份早一點被點亮。`shownRes` 不在 `buildView()` 的輸出裡，
  不影響逐點比對，但會影響最終存檔雜湊。
- **真人錄製只有幾小時**，`compare_runs.js` 只比重疊區間，不外插。

### 換裝改成只看「洗不掉的東西」（採用，收益有限）

一件裝備上真正永久固定的只有品質（詞條數＋插槽數）、裝等、太古位置數；
詞條鍵與數值可以洗、強化可以重堆、寶石可以拔下來重鑲。舊的 gain/need 拿
**候選當下的隨機骰值**去比**身上那件的骰值**，等於讓一次幸運骰把整個部位鎖死——
實測關卡 128 的角色站在掉裝等 100 的關卡、身上最弱部位還是裝等 50。

改成「高一階（品質或裝等，另一項不更差）就直接換，除非身上那件的太古多 3 條以上」。
A/B（20 小時 × 8 seed，同 seed 配對）：

| 指標 | 對照 | 新版 |
|---|---|---|
| 等級 | 186.5 | 177.5（3/8 贏） |
| 關卡 | 146.5 | **150**（6/8 贏） |
| 物攻 | 50,166 | 55,706（5/8 贏） |
| 死亡 | 456 | 387 |

身上裝等從「最低 50」變成 13 件裡 11 件是 100。結構上是對的，但在 R5 那道牆前面
只值 3.5 關——**修好換裝並不能取代內容側的問題**。

### 死亡退關「立刻切回去」——負面結果，機制保留但不啟用

野外死亡退 10 關（`FIELD_DEATH_STAGE_RETREAT`），而 `stage.goMax` 一步就能跳回
`min(best, 地圖上限)`。實測 20 小時死 456 次、`stage.go` 只送 36 次、`stage.goMax`
**一次都沒送過**——角色把那 10 關重打一遍，一次約 3 分鐘。速率相減看起來很有說服力：

    清怪推關 +3.4 關/分（每波 +1 關 × 自動推關開著 70% 的時間）
    死亡退關 −3.8 關/分（0.382 次/分 × 10 關）

於是加了 `resumeBest` 規則（落後 ≥3 關就 `stage.goMax`，安全條件沿用既有的卡關重試
閘門 `ctx.retryWaiting`）。**實測更差**：

| 指標 | 對照 | 換裝 | 換裝＋切回關卡 |
|---|---|---|---|
| 等級 | 186.5 | 177.5 | **141** |
| 死亡 | 456 | 387 | **679** |

它跳回 150 之後又被打死，反覆送死比重爬那 10 關更貴——**那個退關其實是誤打誤撞的
安全閥**，而 `retryWaiting` 擋不住它（它只看菁英／BOSS 的卡點記錄，攔不住「一般怪
就打不過」的情形）。機制留在 `policy_interpreter.js` 的 `resumeBest` 分支，
策略檔不啟用。要重啟得先給它一個真的能判斷「現在回得去嗎」的訊號。

### 換圖：草原打通就是硬牆（已補，尚未實測執行）

關卡改造之後每張地圖都是有限關卡（草原 200／荒漠 300／沼澤 400／亡靈山脈 500）。
打到頂之後 `js/combat.js` 會夾住 `current`、設 `mapComplete` 並停止出怪——
**推關指令照送、遊戲照回 ok，但關卡再也不動**。`stage.switchZone` 在此之前
一次都沒被送過，AI 會在草原 200 關永久停住而且完全沒有徵兆。

規則 `switch-zone-when-cleared`：只有當前這張圖真的打通（best ≥ maxStage）才換，
取「已解鎖、且上限更高」之中設計順序最小的那一張。解鎖與否由遊戲的 `isZoneUnlocked`
回答，不在策略裡抄 `Zones.csv`。端到端驗證過（草原 best=200 → 送出 desert →
遊戲收下並切到荒漠第 1 關；best=150 時不送），但目前 seed 到不了 200，尚未在實跑中執行。

### 強化上限：極端強化是虧的

碎片成本 `8 × 1.35^等級`，成功率 +17 起觸底 30%、失敗付半額。裝等 100 的期望碎片：

| 目標 | 累計期望碎片 |
|---|---|
| +25 | 440,754 |
| +30 | 2,004,659 |
| +35 | 9,017,264 |

**把一件從 +32 推到 +35 要 5,357,090 碎片，足夠把 12 個部位從 +0 推到 +25。**
戰力上 +35 對 +25 是 ×1.22（一件）對 ×1.22（十二件）。所以設 `maxUpgrade: 25`。

例外是帶**全域型詞條**的裝備（`maxUpgradeGlobalAffix: 40`）：`gemEff` 放大**全身**
已鑲嵌寶石（`formula.js` 的 `gemMult = 1 + gemEff/100`），`enhanceSuccess` 直接降低
自己後續每一級的期望成本（+40% 時推到 +35 的總成本降到 56%）。兩條都只出現在
戒指與項鍊、史詩以上。

### 幸運值：不值得堆（負面結果）

`m = ANCIENT_LUCK_WEIGHT_MULT × 幸運/(幸運 + ANCIENT_LUCK_WEIGHT_DENOM)`，
目前 0.5 / 4000，天花板是 `1 + MULT = 1.5`。幸運只有一條詞條、只能上頭盔／戒指／
項鍊、史詩以上，所以最多 4 格。裝等 500、13 個部位，不堆幸運時太古格是 4.42：

| 投入 | 幸運值 | 太古格 | 詞條價值淨得 |
|---|---|---|---|
| 1 格 | 2,904 | 5.47 | −0.36 |
| 2 格 | 5,808 | 5.92 | −1.07 |
| 4 格 | 11,616 | 6.29 | −2.85 |

（淨得 = 多拿的太古格 ×(1.62−1) − 投進去的格數。1.62 = `AFFIX_MAX_VALUE_MULT ×
`ANCIENT_AFFIX_VALUE_MULT`。）**每一級投入都是負的**：成本線性、收益飽和。
`DENOM` 要降到 1500 才讓「投 1 格」翻正，但 2 格以上永遠是負的——真正的天花板是
`MULT`，`DENOM` 只決定爬多快不決定爬多高。策略維持不追幸運值。

## 技能點：24% 的點數投在永遠不會被施放的技能上（2026-08-05）

### 症狀

一場 Lv.152 的存檔，152 點技能點裡有 **37 點（24%）** 壓在強力斬 10／魔法屏障 10／
二連拳 10／再生術 6／奧術衝擊 1 上——這五個**全部沒有裝載**。
`pickAndCastSkill` 只走 `G.player.loadout`，沒裝載的主動技一次都不會被施放。

### 成因：清單長度與裝載格數是兩套獨立的數字

舊做法是三份寫死的學習清單（16／27／39 個）。但裝載格數是
`clamp(4 + ⌊等級/50⌋, 4, 20)`（1 轉後直接 20）——前期只有 4~5 格。
清單第 2~5 名（powerSlash／doubleStrike／manaBarrier／regenerate）在 4~5 格時裝得下，
Lv.50 之後被排名更前的擠掉，**點數就留在原地**，而技能點是 1 級 1 點，不會自己回來。

沒有任何錯誤訊息。遊戲收下 `skill.learn` 回 ok，技能等級真的漲了，只是永遠不施放。

### 兩項修正

`learnPlan`（規則 `learn-skills`）：主動只學**裝載欄放得下的**——名額問
`panels.skills.loadoutSize`，不在策略裡寫死；`always`（再生術／魔法屏障）另外學但不佔常駐格；
其餘點數全投被動。被動不佔裝載欄、學會即常駐，所以是溢出點的唯一正確去處。
`passivePriority` 依物理流的邊際收益排：利刃專精 → 殘暴 → 銳眼 → 迅捷步伐 → 堅韌體魄 →
鋼鐵之膚 → 嗜血本能 → 財運亨通。**刻意不含奧術心智與冥想**：前者是 matkPct（物理流無用），
後者是法力——法力確實是施放門檻（`js/skills.js:2938` mp 不足直接 `continue`），
但那條路徑不留任何日誌，值不值得投要先有計數器才能回答，在那之前不猜。

`deleteUnusedSkills`（規則 `delete-unused-skills`）：`deleteSkill` 是**全額退還**
（`js/skills.js:2219`），所以前期學錯的點不必認賠。三道保護缺一不可——
現在裝載欄裡的不刪（含危險時暫時換上去的）、任何宣告過的清單裡的不刪
（`always` 平時就是「學了沒裝」，不保護會被刪了又學無限迴圈）、
融合技與它的材料不刪（`deleteSkill` 不檢查融合佔用，刪材料會把融合技一起弄壞）。

結果：死點從 37 降到 **0**。順帶修掉兩個一直在空轉的指令流——
`learn-skills` 每 3 小時送 16,440 次「已達最高等級」（面板補送 `maxLv` 後跳過）、
`equip-loadout` 送 3,232 次「尚未學習」（`learnedIn` 過濾）。
總指令數 20,571 → 4,131，存檔雜湊不變。

## 保命技：第一版把「怪物種類」當成了因果（2026-08-05）

### 誤區

直覺的寫法是「打小怪上產出技（點金手／尋寶直覺），打菁英或 BOSS 上保命技
（魔法屏障／再生術）」。**實測 8 個 seed 死亡數全部上升。**

錯在怪物種類與危險只是相關、不是因果：同一隻小怪，裝備夠強就一路輾過去、
不夠強就會掛；BOSS 也一樣，強到不用保命技也能贏就不必上。
而且菁英太密——每 36 遊戲秒就翻一次，等於角色一直在拆裝備、重裝、拆裝備。

### 第二版：問處境，不問怪是什麼

`evalDanger` 產出 0/1/2 三級，訊號有三個，**都取「最壞的那一刻」而不是平均**
（被秒的那一下之前，平均值可能一直很好看）：

| 訊號 | 門檻 | 角色 |
|---|---|---|
| 死亡率（`ctx.deficit.deathRate`，600 秒視窗） | > 0 | **主判準**——「掛一掛會不會死」 |
| 滾動視窗最低血量（300 秒 / 6 桶） | 進 < 50%、出 > 65% | 前導指標 |
| 擋在前面那一關的敵人最佳殘血 | ≥ 30% → 直接第 2 級 | 「差得遠」 |

主判準必須是死亡率，不能只看血量水位：實測一份 Lv.169 存檔在關卡 150 掛 33 分鐘，
**最低血量 57%（高於 50% 門檻）卻仍會週期性死亡**——只看血量會漏掉
「平常很穩、偶爾被秒」這種最需要保命技的情況。

進出門檻刻意不同（50 / 65）：相同的話血量在門檻附近抖動會讓每個決策點都拆一次裝一次；
而且「剛好回到 50%」不代表安全，只代表這一個視窗沒被打到。
攢不滿兩桶回 `unknown` 不猜——開場血量本來就滿，猜「安全」會讓保命技在最需要的前期缺席。

階梯：等級 1 換上魔法屏障、擠掉**尋寶直覺**；等級 2 再換上再生術、擠掉**點金手**。
先擠尋寶直覺是因為點金手是金幣引擎，收益擴散到強化與背包。
換裝載欄本身是免費的（`unequipSkillFromLoadout` 無條件、等級保留、冷卻掛在角色實體上不會重置）。

### A/B（20 小時 × 8 seed，同 seed 配對）

| 指標（最小／**中位**／最大） | A 不切換 | B 危險驅動 |
|---|---|---|
| **死亡** | 396 / **468.5** / 587 | **371 / 443 / 479** |
| 等級 | 114 / **136** / 152 | 104 / **151** / 171 |
| 最高關卡 | 126 / **147** / 150 | 118 / **146.5** / 151 |
| 物攻 | 12,249 / **34,943** / 67,641 | 17,975 / **29,205** / 41,554 |

死亡在三個分位數上全部下降（上緣 −18% 最明顯），逐 seed 6/8 下降。

第二級真的只在打不動的時候才上。這與「魔法屏障除非怪極弱或能秒全場否則必上」吻合。

**這個結果撐不起「證實有效」**：死亡中位只降 5%、6/8 在二項式下純靠運氣的機率約 14%。

原始批次目錄已清除（20 小時 × 8 seed 約 1.6 GB），上表是唯一保留的紀錄。

比較可能的方向是產出技被其他規則擠掉，導致「安全後換回去」變成空操作。尚未查證。

## 掛機關卡：底部 vs 深處，以及一個被實測打臉的推論（2026-08-06）

### 起點

使用者的玩法：「掛 101、151、201 這種會掉下一級裝備且最容易快速殺敵的關卡；
材料跟裝備掉落數的權重比等級高，等級只是在前者都不缺的情況下盡量能衝就衝高。」

查證下來前半段完全正確，而且推翻了程式裡的一句過期註解。關卡改造之後野外掉落
改走 `rollFieldDrops → fieldDropRatesFor → ZONE_STAGE_DROP_TABLE` 查表
（js/combat.js:931），粒度是**關卡區間**，區間之內完全相同：

| | 草原 100 關 | 草原 149 關 |
|---|---|---|
| 掉落率 | R3 10% / R4 1.5% | **完全一樣** |
| 裝等 | 100 | **一樣** |
| 怪物血量 | 1× | 25.79× |
| 經驗 | 1× | 21.25× |

（js/data.js），也就是 **1,241 隻/時**的硬上限。角色在關卡 189 就已經是一擊必殺，
血量少 25 倍完全用不上。

| v6 | 25% | **1,042** | **1,041** | 223 |

| 死亡 | 364 | **313** | 470 | 841 |

逐 seed 的最好與最壞都在 farmPark 這一側：v7 的 seed …389 跑出 **Lv.625 / 關卡 250**
（全場最佳，對照是 519/232），但 v6 與 v7 各有一個 seed 擱淺在關卡 **151/152**
（草原 150 底部，`best` 沒累積到 200，連沙漠都沒進去）。

物攻隨推進占比單調上升（263K → 637K）不是刷出來的，是**跨過裝等 200 的邊界**：
v8 五個 seed 全部站上 200+，而對照有三個停在 193~198，身上還是裝等 150 的裝備。

### 結論與去留

**farmPark 不是等級／關卡的槓桿。** 等級來自經驗，而經驗＝擊殺數 × 每隻經驗；
擊殺數被固定開銷夾住，所以**深度直接決定經驗時薪**，底部反而虧 21 倍。

它真正買到的是**同樣的掉落數 ＋ 少很多的死亡**（v6：擊殺 +4%、死亡 −14%），
而這正是真人掛在 101/151/201 的理由——不是產出更高，是**更安全且不損失掉落**。

保留 25%（`farmSec 1800 / pushSec 600`）：它是唯一同時改善擊殺與死亡的比例，
50% 以上死亡暴增（470 / 841）而等級沒有回報。

### 這一節真正的產出

1. **掉落率是階梯，不是連續的**——`tier.farmFloorStage` / `nextFarmStage` 把整張圖
   切成掛機點（草原 1→21→40→50→100→150→200，荒漠 1→50→200→250→300），
   全部由遊戲的三支函式二分搜出來，掉落表改版會自動跟著改。
2. **擊殺速率有硬上限 1,241 隻/時**，而策略在關卡 189 就已經吃掉 75%。
   任何「讓角色殺更快」的改動，天花板都在這裡——要提高產出只能靠掉落**率**
   （跨區間、掉寶率詞條、熔爐零件），不能靠殺更多隻。
3. **裝等邊界（每 50 關）比關卡本身重要**：v8 全部站上 200 之後物攻是對照的 2.4 倍。

## 神鑄法陣：策略裡一條規則都沒有（2026-08-06）

### 病灶

實測 48 小時 × 5 seed（2 轉、關卡 301）：累積掉落**傳說 2,495 件、神話 175 件**，
而創世只有 **2 件**、神鑄創世 **0 件**。

原因不是解鎖沒到（`forgeUnlocked()` 是 `level>=1 && 轉生>=1`，2 轉早就開了），
而是 `policy.extreme.roi.json` 裡 **`forge.*` 規則數是 0**。
那五條名字帶 forge 的規則全部是 `newforge.*`——**熔爐（分解爐）**，
跟神鑄法陣是兩套系統，只是名字很像。

### 兩個會讓「照直覺做」失效的機制

**1. 產物等級取六件裡最高**（`resolveForge` 的 `maxLv`）

所以只要**一件**高等素材就夠，另外五件同品質垃圾也無所謂。
「存滿六件 300 級傳說再鑄」會把高等素材用掉 6 倍，湊料時間也是六倍。

**2. 遊戲的自動放入取評分最低的六件**（`forgeAutoFillApply` 依 `autoSalvageScore` 升冪）

與第 1 點剛好相反——直接開 `forge.setAutoFill` 會穩定鑄出低等神話。
鎖裝備也救不了（候選條件是 `!it.locked`）。所以只能 `forge.placeItem` 逐件指定。

### A/B（48 小時 × 5 seed，同 seed 配對，程式定版 8f79ba6）

|---|---|---|
| 轉生 | 2 | **3** |

| **物攻** | 9,947,860 | **49,578,715（5.0×）** |

| 死亡 | 395 | 386 |

**物攻是全勝且不重疊**：有神鑄的最小值 24.4M ＞ 對照的最大值 11.3M。

跨不同轉生數比等級沒有意義。

## 幸運值：曲線的形狀對，量級差 40 倍（2026-08-06，負結果）

使用者：「到了神話裝備以上，幸運值是值得投資的，至少出 1 條。」

形狀他說對了。幸運的乘數 `f = 1 + 0.5×luck/(luck+4000)` 是**逐項次方**加權
（`ANCIENT_COUNT_WEIGHTS` 第 i 項乘 `f^i`），權重表越長尾巴被拉得越誇張，
所以詞條數越多幸運越值錢——這正是「400 級以前不太需要考慮」與
「神話以上值得投資」兩句話的同一條曲線。

**但一條詞條買不到那條曲線。** 實測一條幸運詞條只給 **100** 幸運值：

| 幸運值 | 乘數 f | R8（八條詞條）期望太古 | 相對幸運 0 |
|---|---|---|---|
| 0 | 1.0000 | 1.210 | — |
| **100** | 1.0122 | 1.230 | **+0.019** ← 一條詞條 |
| **400** | 1.0455 | 1.283 | **+0.073** ← 四個合法部位全上 |
| 4000 | 1.2500 | 1.652 | +0.442 |
| 20000 | 1.4167 | 2.008 | +0.797 |

### A/B（48 小時 × 5 seed，同 seed 配對，程式定版 6f96868）

| 中位 | 對照 | 有幸運目標 |
|---|---|---|
| 轉生 | 3 | 3 |
| 等級 | **683** | 636 |
| 最高關卡 | **340** | 330 |
| 物攻 | **57,159,681** | 53,409,066 |
| 死亡 | 398 | **395** |

**機制確實觸發了**：4/5 seed 湊到幸運詞條、幸運值 100。
而**太古密度 1.27 對 1.28——完全沒動**。等於拿一格詞條換了零，
所以關卡與物攻小輸是合理的（那一格本來可以放有用的東西）。

已把 `luckAffix` 目標與保留清單裡的 `luck` 移除。

### 真正的旋鈕

- **可行的幸運來源是寶石不是詞條**：太陽石 10 級一顆 = **432** 幸運，
  抵得過四個詞條部位全上。之後真要投資幸運，入口在鑲嵌偏好（`socketEmpty`），
  不是洗煉目標。
- **`ANCIENT_LUCK_WEIGHT_DENOM = 4000`** 決定了有用區間的位置。
  目前這個值把有用區間放在詞條完全構不到的地方。

`tests/sim-luck-target.test.cjs` 留下兩支哨兵：曲線形狀的單調性
（機制決定的，參數怎麼調都不該破），以及「一條詞條的增量 < 0.05」——
使用者若把 DENOM 調小，那支會紅，那正是「幸運值現在有用了，可以把目標加回來」的提醒。

### 順帶修好的一個結構性洞（未單獨 A/B）

`reroll-by-roi` 挑犧牲品純看 ΔDPS/ΔEHP 的損失，而**價值不出現在戰鬥面板上的
詞條損失恆為 0**：`luck` / `gemEff` / `loot` / `xpBonus` / `enhanceSuccess` / `cdr`
全部如此。於是它們永遠是損失最小的那一條，也就永遠第一個被犧牲——
`reroll-by-roi` 系統性地拆掉 `reroll-for-deficit` 剛湊起來的東西。

實測 24 小時 × 5 seed：`gemEff` / `loot` / `xpBonus` 三個目標都宣告 `atLeast 3`，
結果全身合計只有 **2 / 5 / 3** 條。

修正：宣告過的詞條目標「再少一條就不達標」時，那條不准當犧牲品。
⚠️ 這個修正**兩組都有**（對照組只拿掉 luck），所以上面的 A/B 沒有量到它。
它的效果要另外驗。

## 強化成功率：飾品三格已經超賣（2026-08-10，負結果）

實測 48 小時 × 5 seed 的結局存檔，全身 60 件裝備裡 `enhanceSuccess` 是 **0 條**。
它在保留清單裡（洗到了不會被洗掉）但沒人去追，而 ROI 也追不了——
它的價值不出現在 ΔDPS/ΔEHP 上，排序永遠是 0。所以宣告成目標。

### A/B（48 小時 × 5 seed，同 seed 配對，程式定版 fec97cb）

| 中位 | 對照 | 有目標 |
|---|---|---|
| 轉生 | **2** | 1 |
| 最高關卡 | **300** | 296 |
| **物攻** | **10,952,651** | **4,685,082** |
| 死亡 | 515 | **421** |

**物攻 5/5 seed 全輸**，中位掉 57%。

### 為什麼

| | 對照 | 有目標 |
|---|---|---|
| **enhanceSuccess** | **1** | **1** ← 目標沒讓它變多 |
| gemEff | 8 | **6** |
| loot | 6 | **5** |
| xpBonus | 7 | **4** |
| `reroll-for-deficit` 送出 | 2,577 | **4,618**（+79%） |
| 結局精華 | 54,962 | **27,227** |
| 強化等級 中位 | 25 | 25 |

**飾品三格已經超賣。** `enhanceSuccess` 的合法部位只有戒指×2 與項鍊，
而那三格已經有 `gemEff` / `loot` / `xpBonus` 三個 `atLeast 3` 的目標在湊。
再加第四個只是把精華攤薄到四個目標上——結果**一個都湊不滿**，
自己沒多拿到一條，還把另外三個一起拖下水，精華燒掉一半。

### 附帶確認：強化等級的瓶頸不是成功率

兩組的強化等級中位**都是 25**，正好是 `upgradeByRoi.maxUpgrade` 的寫死值。
所以「強化停在 25」的原因是那個上限，不是成功率不夠。
把 `maxUpgrade` 改成看實際成功率動態決定，才是那條線的正解——這項仍未做。

### 可帶走的規則

**宣告目標要看部位預算。** 目標是搶同一批詞條格的，而每個部位的格數是固定的
（品質決定，R7 七條、R8 八條）。同一組部位上的目標數量 × atLeast
不能超過那組部位的總格數扣掉必要的傷害詞條——超賣的結果不是「多拿一點」，
而是每一項都拿不到。

## maxUpgrade 25 vs 32：分不出來（2026-08-11）

### 起點是一個被推翻的假設

先前兩批 A/B 的強化等級中位**都正好是 25**，於是我提議「把 `maxUpgrade` 改成
看實際成功率動態決定」。查了公式之後那個提議不成立：

```
upgradeSuccessBase：+5 以內必成，之後每級 −6 點，下限 30%
  +10 → 70%    +17 → 30%    +25 → 30%    +40 → 30%
```

**從 +17 之後成功率鎖死在 30%，再也不變。** 沒有任何訊號可以拿來當停止條件。
`enhanceSuccess` 也不是解鎖更高等級，它只降低每次嘗試的期望成本。

真正的牆是碎片成本，`8 × 1.35^等級 × (1 + 裝等 × 0.04)`——指數的。
裝等 300 的裝備：

| 推一級 | 碎片 |
|---|---|
| +24 → +25 | 139,651 |
| +29 → +30 | 626,199 |
| +34 → +35 | 2,807,899 |
| +39 → +40 | 12,590,713 |

一件從 +25 推到 +40 要 **48,025,524** 碎片；一件從 +0 推到 +25 只要 538,356。
**等於 89 件。** 所以 `maxUpgrade: 25` 的分散投資理由是硬的。

### 掃描（48 小時 × 5 seed，同 seed 配對，程式定版 9045afc）

| 中位 | 25 | 32 |
|---|---|---|
| 轉生 | **2** | 1 |
| 最高關卡 | 251 | **294** |
| 物攻 | 9,395,318 | **9,765,747**（+4%） |
| 擊殺 | 72,443 | 72,451 |
| 死亡 | 533 | **421** |

**分不出來。** 物攻逐 seed 是 3:2、關卡 3:2 偏 32，但轉生次數偏 25，
而且變異極大（25 的物攻 3.0M~14.2M、32 的 5.2M~22.6M）——
兩組的全距幾乎完全重疊，5 個 seed 在這個雜訊水準下沒有解析度。

**維持 25。** 沒有證據支持改動，而成本math 站在 25 這一邊。
要真的分辨得出來，需要的是更多 seed 而不是更長時間——
變異來源是 seed 之間的軌跡分岔，不是單場的收斂不足。

⚠️ 這批的絕對數字（物攻中位 ~9M）與更早的神鑄批次（~50M）**不可比**：
中間使用者調過敵人強度與掉落物。跨批次只能比同批的兩組。
