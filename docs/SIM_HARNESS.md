# AI 玩家模擬器（原生內核 headless）

## 這是什麼

用**遊戲本體的程式碼**跑 AI 玩家掛機模擬。所有數值——傷害、掉落、經驗、成本、機率、
日誌文字——都由遊戲自己算；harness 只負責推進時間、在決策點問策略、把指令送進遊戲。

harness 內沒有任何遊戲公式或常數。這不是靠自律，是靠結構（見「隔離」一節）。

---

## 怎麼跑

```bash
node --max-semi-space-size=64 scripts/run_sim.js --hours=100 --seed=20260730
```

| 腳本 | 用途 |
| :--- | :--- |
| `scripts/run_sim.js` | 主模擬，輸出存檔／快照 CSV／原生事件／執行摘要 |
| `scripts/bench_sim.js` | 純效能量測（無策略） |
| `scripts/verify_equivalence.js` | 決定論 + 改造等價性 + 種子敏感度 |
| `scripts/test_policy_isolation.js` | 策略層隔離反證（每項都必須失敗） |
| `scripts/cross_check.js` | 真瀏覽器 ↔ headless 逐檢查點比對 |
| `scripts/verify_trace.js` | 真人錄製 ↔ 軌跡重播逐檢查點比對（見「真人基準線」） |
| `scripts/compare_runs.js` | 兩場模擬的曲線對照（真人 vs AI） |
| `scripts/proxy_guard_ab.js` | Proxy 守門方案的行為中性 A/B 判定 |

策略檔（資料，非程式）：

| 檔案 | 用途 |
| :--- | :--- |
| `scripts/sim/policy.default.json` | 從零開始的掛機策略。看成長曲線用這份 |
| `scripts/sim/policy.lategame.json` | 以 GM 墊出已轉生角色，專門驗證天賦／神鑄／高塔會不會動。**不能拿來談成長曲線** |

`--max-semi-space-size=64` 是 GC 調參，實測比預設快約 1.4 倍，不影響結果。

輸出在 `sim_out/`（已 gitignore）：

- `save_final.json` — 可直接匯入遊戲續玩
- `snapshots.csv` + `snapshots.meta.json` — 圖表資料與**每一欄的來源標註**
- `native_events.jsonl` — 遊戲原生 blog/flog/loot/notice 事件（非 harness 自組）
- `run_summary.json` — 效能實測、指令統計、事件計數、狀態雜湊

## 架構

```
run_sim.js（驅動）
   │  推進時間 → engine.step(n)          每步 dt = TICK_MS/1000 = 0.1s，不放大
   │  觀測     → engine.view()           = 原生 buildView()
   │  決策     → policy.decide(深拷貝)    隔離 context，見下
   │  送指令   → engine.cmd(name, args)  = 原生 runCommand()
   ▼
sim/engine.js（宿主）
   │  把 js/worker/sim.worker.js 原封不動載進 vm context
   │  它自己 importScripts 那 20 支模擬層檔案，載入順序與線上完全一致
   ▼
遊戲本體
```

### 只替換「瀏覽器環境」，不替換遊戲

| 替換項 | 為什麼 |
| :--- | :--- |
| `Math.random` → 種子化 PRNG | 沒有決定論，任何比對都做不下去。單一注入點，公式檔案一行不改 |
| `Date` / `performance` → 虛擬時鐘 | **關鍵**：`js/item.js:263` 的寶石商店與 `js/forge.js:486` 的熔煉完成都讀真實時鐘。縮時上千倍時真實時鐘幾乎沒走，這兩個系統會整場靜止 |
| `postMessage` / `importScripts` / `setTimeout` | Worker 環境替身 |

### 時間推進的正確性

- 步長固定 `0.1s`，與線上 `TICK_MS` 相同。**放大 dt 換速度＝換一個遊戲**，不做。
- 每 2 步（模擬時間 5Hz）跑一次 `loop()` 的 `updateShownRes` / `maintainGemShop` /
  `checkForgeUnlockNotice`。這三支不在 `simStep` 內，但會刷新寶石商店與解鎖熔爐，
  只呼叫 `simStep` 會讓這兩個系統整場不動。

## 隔離：策略層碰不到遊戲狀態

策略跑在一個**沒有 `G`、沒有 `FIELD`、沒有 `require`、沒有 `process`** 的獨立 vm context，
只拿得到 `buildView()` 的深拷貝，只能回傳「指令名 + 參數」。

這是**能力剝奪**，不是執行期偵測。拿不到參照的東西不需要被監控。

`scripts/test_policy_isolation.js` 逐項反證（12 項全部必須失敗），並附對照組確認策略仍能正常決策。
`Math.random` 與 `Date.now` 在策略 context 內被改成呼叫即拋錯——策略有隨機性或讀真實時間，決定論就沒了。

### 為什麼不用 Proxy 包住 G

1. 包不住。戰鬥狀態在 `js/combat.js:5` 的 module-level `FIELD`，不在 `G` 裡。
2. 成本壓在每次屬性存取上，而要防的事只發生在決策的那一瞬間。
3. **會改變遊戲行為。** `js/battlefield.js:186` 的 `bfLiveList(...).indexOf(locked)` 與
   `js/combat.js:665` 跨 tick 持有的 `_lockTarget` 都依賴物件識別比對，
   每次 `get` 新建 Proxy 會讓比對必定失敗。

第 3 點不是推論，`scripts/proxy_guard_ab.js` 實測過（見下）。

## 已驗證的事實

| 檢查 | 結果 |
| :--- | :--- |
| 決定論（同 seed 兩次 → G 雜湊相同） | ✅ |
| 種子敏感度（不同 seed → 雜湊不同） | ✅ |
| `updateShownRes` early-skip 改造前後等價 | ✅ 雜湊相同 |
| 策略層隔離反證 12 項 | ✅ 全部擋住 |
| **真瀏覽器 ↔ headless 交叉驗證** | ✅ **275 個檢查點全部一致** |
| 既有測試 664 支 / `npm run build` | ✅ 全綠 |

### 交叉驗證（最有力的一道）

seed=779，真 `index.html` + 真 Worker + 真 IndexedDB，跑 55 遊戲秒，每 0.2 秒一個檢查點，
`buildView()` 全部 24 個欄位逐欄比對：**275 個共同檢查點完全一致**。

harness 只要在任何地方偷算過一次，這裡就會分岔。

**做法**（Antigravity 要重跑時照這個順序）：

1. `preview_start` 起本機伺服器（`.claude/launch.json` 已有多組 port）
2. 瀏覽器開 `http://127.0.0.1:<port>/index.html?seed=779`
   ⚠️ 用 `127.0.0.1` 而不是 `localhost`——不同 hostname 是不同 origin，
   才不會去讀（或覆寫）既有存檔
3. 在頁面上掛收集器：
   `window.__x={rows:[]}; WorkerBridge.on('tick',m=>m.view&&__x.rows.push(m.view))`
4. 讓它跑 1 分鐘以上，把 `JSON.stringify(__x.rows)` 存成檔案
5. `node scripts/cross_check.js <那個檔案> 779`

**測試模式的差異（必須連同結果一起說明）**

帶 `?seed=N` 且 hostname 為本機時，Worker 會進入決定論測試模式
（`js/worker/sim.worker.js` 檔頭 `installTestSeed`），與正式遊玩有三處差異：

1. `Math.random` 換成種子化 mulberry32
2. 每個計時器週期固定走一整步，不補欠帳、不走殘步
3. 維護區塊（`updateShownRes`/`maintainGemShop`/`checkForgeUnlockNotice`）改以**步數**計時
4. 一律以全新角色開機，不讀存檔、不落地存檔

**第 2、3 點不是可有可無的**。正式路徑每輪最後會走一個不足 0.1 秒的殘步，
長度取決於真實計時器抖動——連同一個瀏覽器跑兩次都不會一樣，比對在結構上就做不到。
維護區塊照真實時間跑也有同樣問題：`maintainGemShop` 首次會呼叫 `rollGemShop()` 消耗亂數，
它落在第 2 步還是第 3 步會讓整條亂數序列岔開。

所以這道驗證證明的是「headless ≡ 測試模式的瀏覽器」，兩者與正式遊玩的差距就是上面那幾項。

### Proxy 守門 A/B（20 遊戲分鐘，seed=4242）

| 變體 | G 雜湊 | 結果 |
| :--- | :--- | :--- |
| 不裝守門 | `e265152d…` | Lv.7 stage 2 gold 98,695 |

## 效能

實測（Windows / Node，`--max-semi-space-size=64`）：

| 項目 | 數值 |
| :--- | :--- |
| 吞吐 | 約 10,000～12,000 步/秒 |
| 縮時倍率 | 約 1,000～1,200x |
| 10 遊戲小時 | 34.5 s |
| **100 遊戲小時** | **約 5.7 分鐘** |

倍率是**量測值**，每次 `run_sim.js` 都會把實測寫進 `run_summary.json`，不是設定值。

已做的優化（全部經雜湊驗證等價）：

1. `js/worker/sim.worker.js` 的 `updateShownRes` 加上 early-skip——旗標設了就不再重算。
   改造前它（含 `totalGemsAll`）佔 headless 總 CPU 的 **39%**，只為決定頂欄圖示要不要顯示。
   瀏覽器端每秒也跑 5 次，玩家機器同樣受益。
2. `Math` 用自有屬性複本而非 `Object.create(Math)`，避免每次 `Math.floor` 走原型鏈。
3. GC 調參。

再往下要更快，只能優化遊戲引擎本身的熱路徑（`talentState` / `forgeState` / `skillDef`
等每擊重複查找，以及 `battlefield` 的每擊陣列配置）。profile 已經平坦，
最大單項 `fieldTick` 只佔 9%，沒有便宜的大獎了。

## 遊戲改版時要不要同步給模擬器？

**預設：不用。** 數值、公式、常數、機率、掉落表、失敗訊息全部是從遊戲讀的，
改了模擬器隔天自動跟上。連寶石種類都是 `{"path": "panels.gems.gems"}` 取出來的，
新增第 39 種寶石不需要改任何清單。

但有三件事改了會讓模擬**靜靜失真**——不是壞掉，是安靜地測不到。
所以不靠「記得同步」，改成三個會自己叫的哨兵：

| 會失真的情況 | 哨兵 | 在哪裡看 |
| :--- | :--- | :--- |
| `loop()` 新增第四支維護函式，headless 沒跟上 | `tests/sim-harness-sync.test.cjs` | `npm test` 直接紅燈 |
| 面板欄位改名，策略的 `$path` 指到舊路徑 | 路徑解析失敗計數 | `run_summary.json` 的 `badStatePaths`，跑完也會印在終端 |
| 新增玩家指令，策略沒有對應規則 | 指令覆蓋率 | `run_summary.json` 的 `untestedCommands` |

第三項不一定是問題（有些指令本來就不該由 AI 用），但它是「策略還沒覆蓋什麼」的客觀清單——
遊戲新增系統時，新指令會自動出現在那裡，等於待辦清單自己長出來。

前兩項都做過反證測試，確認**真的會叫**：
故意從 `MAINTENANCE_FNS` 拿掉一支 → 測試紅燈並指出差異；
故意把 `panels.tower.tower.highest` 打成 `highestFloor` → `badStatePaths` 抓到。

## 指令成效怎麼讀

`run_summary.json` 的 `commands` 分成四類，**不要只看「送出」**：

| 欄位 | 意思 |
| :--- | :--- |
| `effective` | 真的做到了 |
| `noEffect` | 沒做到，`reasons` 是**遊戲自己給的原話**（如「技能點不足」「金幣不足（需要 5.02K）」） |
| `unknown` | 指令無回傳值（如 `js/tower.js:95` 的 `startTowerAuto`），要看原生日誌才知道結果 |
| `error` | 協議層就被擋下（指令名或參數不合法） |

⚠️ 模擬層的回傳慣例與直覺相反：**`null` 是成功、字串是失敗原因**
（`js/skills.js:2129` 成功時 `return null`，失敗時 `return '技能點不足'`）。
天真地判斷 truthy 會把 1200 次失敗全部算成成功——這個坑踩過一次。

## 目標與缺口：讓策略自己發現該補什麼

策略原本寫的是**「該做什麼」**——一份靜態的詞條保留清單。問題是正確答案會隨關卡改變：
怪物閃避在關卡 130 是 86.8%、關卡 150 是 103%，而命中公式夾在 5%～100%。
所以命中率詞條在關卡 100 不需要、在關卡 146 是唯一解——**任何固定名次都是錯的**。

實測後果：角色面板命中 100%、身上 65 條詞條一條命中率都沒有，有效命中觸底 5%，
13,718 次出手只中 551 次。而策略完全不知道，它以為自己物攻 91K 很強。

改成宣告**「要達成什麼」**（`policy.targets`）：

```json
{
  "id": "hit",
  "kind": "selfMinusEnemy",
  "self": "panels.equip.stats.hit",
  "enemy": "ctx.enemyDodge",
  "clampMin": 5, "clampMax": 100,
  "atLeast": 95,
  "affixKey": "hit",
  "avoidSlots": ["ring", "amulet"],
  "preferSlots": ["boots", "legs", "wrist", "helmet", "gloves"],
  "maxAffixes": 4
}
```

直譯器每個決策點算出缺口掛在 `ctx.deficit.<id>`，`rerollForDeficit` 規則據此主動洗出
補缺口的詞條，補滿自動停手。**不需要有人回去改清單。**

實測（重度、100h 牆鐘、4 個 seed）：

| | 等級（最小/中位/最大） | 關卡（最小/中位/最大） |
| :--- | :--- | :--- |
| 無目標 | 105 / **161.5** / 454 | 133 / **149** / 206 |
| 缺口驅動 | 185 / **242.5** / 305 | 173 / **177.5** / 207 |

中位數關卡 149 → 177.5，最差的一次從 133 拉到 173，散佈明顯收窄。
⚠️ 對照組有一次跑到 Lv.454——那是運氣。**單一 seed 比較會得到相反的結論**，
這類判斷一律要多 seed。

### 三個實測踩過的坑

- **可用部位一律從遊戲讀**（`panels.equip.affixRules`，協議 v15），不要在策略裡手抄。
  抄過一次就錯了：寫了 `weapon`（命中率不能出現在武器上）與 `bracers`（遊戲的鍵是
  `wrist`），375 次洗煉一條都沒洗出來，而且沒有任何錯誤訊息。
- **試次只能算「真的洗到了」的**。策略層看不到指令結果，但看得到詞條有沒有變。
  不分辨的話，資源不足的空轉會把試次燒光然後永久放棄——實測 832 次嘗試有 579 次
  是資源不足，於是所有部位在沒洗到半次的情況下被判死刑。
- **不要讓「缺口未補滿」永久改變行為**。試過在缺口未補滿時禁止換掉帶有該詞條的裝備，
  結果從關卡 190 掉到 117：目標訂了達不到的值，於是保護變成永久凍結，裝備停止升級。
  任何「缺口未補滿時就……」的規則都要能在目標達不到時自己收手。

## 產出閘門：一場關於「誘因」而不是「策略」的實驗

> **現況（2026-08-02 決策）**：離線收益維持原本的設計——**以歷史最高關卡為基準的
> 固定費率**，不看命中率、不看怪物血量、也不看玩家傷害。強度改由參數表調整
> （見下方「參數表旋鈕」）。因此**六份策略的產出閘門都關閉**：在這個誘因結構下
> 它實測會讓成績變差。要啟用只需在 `stageGate` 加 `requireTargets` / `targetRetreat`
> 兩個欄位，機制與測試都在。
>
> 這一節照時間順序保留，因為那個順序本身就是結論：
> **策略怎麼調都調不動的時候，要先確認遊戲在獎勵什麼。**

### 動機

命中率、傷害、抗性都是**原因**；`player_strategy.md` 對安全關卡的定義量的是**結果**——
「能在平均 3 秒內殺死一個敵人」。原本三道閘門（裝備品質覆蓋率、卡關重試、以及
上面的詞條缺口）量的全是投入，而實測會脫節：一場全身史詩、沒死過、重試閘門也沒攔，
卻在關卡 150 之後每分鐘殺 0～1 隻，**整整 24 個在線小時零掉落零經驗**，三道閘門一道都沒響。

所以加了第四種目標度量 `ratePerMin`（計數器的滾動視窗差分）與兩個 `stageGate` 欄位：

```json
{ "id": "killRate", "kind": "ratePerMin",
  "counter": "panels.battle.lootStats.sources.field.kills",
  "windowSec": 300, "atLeast": 20 }
```
```json
"requireTargets": ["killRate"],
"targetRetreat": { "step": 5, "everySec": 300, "minStage": 1 }
```

`requireTargets` 裡有目標**已知**未達標時關掉自動推關，`targetRetreat` 再每
`everySec` 往回退 `step` 關，直到殺得動為止。`unknown`（視窗還沒攢滿）不算未達標。

門檻 20 隻/分不是憑感覺挑的——實測 100 小時的速率剖面：

| 關卡段 | 10–80 | 90–140 | 150+ |
| :--- | ---: | ---: | ---: |
| 中位速率（隻/分） | 21–31 | 3–13 | **0–1** |

| :--- | ---: | ---: | ---: | ---: |
| 不設閘門 | 86 / **199** / **322** | 109 / **160.5** / **200** | 33,564 | 108 |
| ≥2 隻/分 | 86 / 174.5 / 279 | 100 / 136 / 150 | 35,992 | 102.5 |
| ≥5 隻/分 | 101 / 188 / 257 | 116 / 135 / 160 | 43,192 | 126 |
| ≥10 隻/分 | **147** / 194 / 256 | **131** / 145.5 / 150 | **49,268** | **74** |

門檻 20（指南建議值）單 seed 就崩了：Lv.322 → **Lv.85**、關卡 188 → 100，
而且**擊殺數翻倍**（26,928 → 54,467）。機制完全照設計運作，只是設計本身瞄錯了。

### 為什麼：離線結算不檢查「你打不打得動」

拿那一場跑完的存檔（Lv.322、關卡 188、命中 163.18、物攻 84,932）直接問遊戲。

**先排除一個嫌疑：數值曲線本身沒問題。**

| 關卡 | 血量 | 經驗 | 經驗 ÷ 血量 |
| ---: | ---: | ---: | ---: |
| 90 | ×1.0 | ×1.0 | ×1.00 |
| 130 | ×14.8 | ×12.2 | ×0.83 |
| 188 | ×626.3 | ×442.9 | **×0.71** |

血量與經驗幾乎同步成長，「每點傷害換到多少經驗」98 關只差 0.71 倍——
**線上收益本來應該與關卡深度幾乎無關**。

**那這一場為什麼打不動？因為裝備停止更新了。**

| 關卡 | 怪物閃避 | 有效命中率 | 線上收益（相對 90 關） |
| ---: | ---: | ---: | ---: |
| 90 | 56.2 | 100.0% | ×1.00 |
| 130 | 86.8 | 76.4% | ×0.63 |
| 188 | 141.0 | **22.2%** | **×0.16** |

這份存檔的面板命中卡在 163.18，關卡 188 的普通怪要 1,925 次命中才打得死，
實測每分鐘擊殺數 0～1。

⚠️ 當時我把這張表讀成「閃避曲線甩開了命中」，**那個歸因是錯的**——
修好離線之後同一份策略的四場實測，有效命中率在各自的刷關關卡全是 100%。
真正的因果是反過來的：漏洞讓 AI 停在原地掛機 → 裝備不再更新 → 命中才追不上。
詳見下面「那道命中牆也一起消失了」。

**而 `applyOfflineProgress`（js/save.js:941）這三件事一件都不看**：命中率、怪物血量、
你的傷害。它只做 `elapsed ÷ 20 秒 = 擊殺數`，再乘上 `offlineStageFor(G.stage.best)`
那一關的**菁英怪**（普通怪的 2 倍經驗）單殺價值。於是在關卡 188：

| | 每分鐘擊殺 | 對象 |
| :--- | ---: | :--- |
| 離線公式給的 | **3.0** | 菁英怪 |
| 線上實測做得到的 | **0.0 ～ 1.0** | 普通怪 |

| `stage.best` | 離線結算關卡 | 單殺經驗 | 16h 離線可升幾級 |
| ---: | ---: | ---: | ---: |
| 50 | 40 | 3,105 | 7.0 |
| 100 | 90 | 75,071 | 14.8 |
| 140 | 130 | 919,235 | 60.3 |
| 188 | 170 | 10,967,792 | **321.5** |
| 200 | 190 | 37,601,072 | **789.4** |

⚠️ 3 隻/分這個速率本身不算慷慨——`best=50` 時離線只有線上的 **0.2 倍**，前期它確實
比線上慢，正如直覺所料。**問題是它沒有被任何「打得動嗎」的檢查夾住**：關卡數一旦
跑贏傷害，這個固定費率就變成在發放角色根本做不到的擊殺。而它吃的是**歷史最高**
而不是當前關卡（`stageGo` 只改 `current`，`best` 是單向棘輪，js/combat.js:801），
所以退關也不會讓它縮水——推得深成了免費棘輪。班表下離線佔 2/3 的時間。

這就是產出閘門必輸的原因：退關省下的在線時間是線性收益，而它換掉的是一個
**與你的傷害脫鉤、隨關卡指數成長**的離線收入。

> **模擬器找到了一個設計沒打算給的最佳解**——「推到推不動為止然後掛機」。
> AI 停在關卡 188 一隻都殺不掉看起來很蠢，其實在那個公式下是對的。
> 策略層再怎麼調都贏不過這件事，因為它調的是行為，而問題出在報酬。

### 曾經試過的修法（已回退，量測結果保留）

做過一版「離線擊殺速率取線上實測值當下限」：野外擊殺時記錄實測速率，
離線結算取 `max(固定費率 20 秒, 實測間隔)`。它有效，但**引入了一個原設計沒有的概念**
（速率量測必然帶一個時間窗），最後決定不採用，改成把強度交給參數表。

保留下來的三個技術結論，日後若要重做請先讀：

| 邊界 | 不處理會怎樣 |
| :--- | :--- |
| 不能用「血量 ÷ 傷害」推算 | 漏掉技能、連擊、範圍攻擊，只算普攻會低估實際輸出約 **5 倍**，等於全面砍收益 |
| 暖機：分子分母要分開衰減 | 只維護「速率的移動平均」要一個時間常數才暖機完，開局 120 秒低估 5 倍 |
| 離線回來要重設時間錨點 | 否則回來打的第一隻怪會把整段離線時間算成「打不動」，之後再也領不到離線收益 |

### 第二輪實測：把誘因改掉之後，同樣的閘門變成最大的一筆改善

在**那個已回退的修正版本**上重跑同一組 seed（重度、100 小時、4 個 seed）。
這組數字現在的用途是回答一個假設性問題：**如果離線不再獎勵「掛在打不動的關卡」，
產出閘門值不值得開**——答案是非常值得。

| 變體 | 等級 最小/中位/最大 | 關卡 最小/中位/最大 | 擊殺 中位 | 死亡 中位 |
| :--- | ---: | ---: | ---: | ---: |
| 不設閘門 | 86 / 118 / 191 | 109 / 141.5 / 192 | 33,574 | 108 |
| ≥5 隻/分 | 101 / 188 / 257 | 116 / 135 / 160 | 43,192 | 126 |
| ≥10 隻/分 | 147 / 194 / 256 | 131 / 145.5 / 150 | 49,268 | 74 |
| **≥15 隻/分** | **196 / 299.5 / 343** | **150 / 150 / 160** | 52,356 | **41** |
| ≥20 隻/分 | 97 / 212 / 322 | 100 / 134.5 / 150 | 52,977 | 38.5 |
| ≥25 隻/分 | 52 / 53.5 / 74 | 42 / 46.5 / 87 | 51,899 | 56 |

- 不設閘門的中位等級從 199（漏洞版）掉到 118——**漏洞值大約 80 級**
- 掛上 15 隻/分之後中位等級 **299.5**，比漏洞版的 199 還高
- 門檻有明確最佳點：25 太嚴（鎖在關卡 42）、20 變異大、15 全面最佳

關卡，速率上限自然從未生效——這正好反證修改只影響了它該影響的那一種情況。

> **這一節真正的教訓**：第一輪的結論「產出閘門沒用」是對的觀測、錯的歸因。
> 策略怎麼調都調不動的時候，要先確認遊戲有沒有在獎勵你不想要的行為。
> 模擬器最有價值的用途不是驗證策略，是**讓遊戲的誘因結構自己暴露出來**。

### 參數表旋鈕（`10-離線`）

離線模型的強度全部收斂到這幾格，程式不再寫死任何一個：

| 名稱 | 參數 | 預設 | 意思 |
| :--- | :--- | ---: | :--- |
| 有效離線時間 | a | 24 | 離線收益時數上限 |
| 擊殺速率 | a | 20 | 每 a 秒 1 隻（20 秒＝**每分鐘 3 隻**） |
| 計算等級 | a | 10 | 從歷史最高階段扣掉多少 |
| 計算等級 | **b** | 10 | 取整單位（扣減後捨去到 b 的倍數；設 1＝不取整） |
| 計算等級 | **c** | 1 | 關卡比例（先乘再扣減；設 0.5＝只算一半深度） |
| **怪物種類** | a | 1 | 1＝菁英（經驗與掉落倍率都較高）0＝普通 |

離線關卡 `= max(1, ⌊(歷史最高 × c − a) / b⌋ × b)`。預設值等於改動前的公式，
`tests/offline-stage-params.test.cjs` 有哨兵盯著這一點。

⚠️ **粗體那三格還沒進 Excel**。`config/CSV/game_parameters.csv` 是由
`config/Excel/game_parameters.xlsx` 產生的（`套用參數.bat` 第 2 步），直接改 CSV
下次轉檔就被蓋掉。程式已經支援，`apply_params` 會把還沒提供的格子列在
「參數表尚未提供」清單裡並沿用程式內的預設值——補上 Excel 欄位就自動生效。

### 那道「命中牆」也一起消失了——它本來就是漏洞的症狀

離線修好之前，關卡 188 的有效命中率只有 22.2%，看起來像是
`4-野外怪物／閃避率` 的成長曲線甩開了角色命中。修好之後回頭量四份存檔，
**四場的有效命中率在各自的刷關關卡都是 100%**：

| seed | 等級 | 刷關關卡 | 面板命中 | 怪物閃避 | 有效命中 | 身上命中詞條 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20260730 | 343 | 154 | 230.6 | 107.0 | **100%** | 2 條 |
| 20260731 | 196 | 145 | 220.5 | 98.8 | **100%** | 1 條 |
| 20260801 | 326 | 146 | 362.7 | 99.6 | **100%** | 3 條 |
| 20260802 | 273 | 135 | 210.9 | 90.8 | **100%** | 2 條 |

原因是命中率詞條的值是 `(基礎值 + 成長基礎值 × 每級 × (裝備等級−1)) × 品質倍率`，
**品質倍率才是主導項**：一條傳說 Lv100 的命中率詞條就是 **+29.8%**，神話 Lv150 是 **+50.5%**。
閃避每階只長 0.5～1.5。所以只要裝備跟得上，命中根本追得上——這幾套裝備
把剩下的詞條格全洗成命中率的話還能再加 950～1250%。

**先前那個 22.2% 是掛機造成的**：AI 停在關卡 188 不動，裝備從此不再更新
（面板命中卡在 163），於是看起來像數值曲線的問題。只要角色持續刷關，
裝備升級與缺口洗煉會一起把命中頂上去，`4-野外怪物／閃避率` 完全不必動。

⚠️ 這是**第三次**在同一件事上改歸因（先怪離線太強、再怪深度主導、再怪閃避曲線）。
前兩次錯在只看了症狀所在的那一份存檔。教訓是：**在行為已經扭曲的狀態下量到的任何
數值曲線問題，都要在行為恢復正常之後重量一次**——症狀會跟著消失，而在那之前
所有歸因都不可信。

### 只要角色在刷關，節奏就是正常的跑步機

在有持續刷關的那組實測裡，到 100 小時仍在往前推（60h 關卡 135 → 80h 145 → 100h 154），
物攻 372 → 176,368，沒有牆也沒有停滯。限制是一般的跑步機——怪物血量每階 ×1.06，
傷害得同步成長，後期大約每 20 牆鐘小時推進 10 關。
這是節奏設計問題，不是失衡；要調快就調 `4-野外怪物／生命` 的指數底，或加快裝備取得。

### 目前的設定與哨兵

**六份策略都沒有啟用產出閘門**——在現行的離線誘因下它實測會讓成績變差
（第一輪那張表）。機制、測試與哨兵都留著，要開只需在 `stageGate` 加：

```json
"requireTargets": ["killRate"],
"targetRetreat": { "step": 5, "everySec": 300, "minStage": 1 }
```

並宣告一個 `ratePerMin` 目標（counter 指向 `panels.battle.lootStats.sources.field.kills`）。
**若日後調整 `10-離線` 的參數讓線上刷關重新划算，記得回來重跑一次這個 A/B**——
第二輪那張表就是在那種前提下量的，門檻 15 隻/分全面最佳。

三支哨兵（`tests/policy-keys.test.cjs`）盯著這個機制最容易靜默失效的地方：
`requireTargets` 必須指到宣告過的目標、退關間隔不得短於取樣視窗、
計數器路徑必須在真實面板裡解得出來（實際開一場遊戲打到有擊殺再解一次）。

### 這個機制自己踩過的兩個坑

- **離線會偽造出「打不動」**。`state.gameTimeSec` 是含離線的牆鐘（`engine.gameTimeSec()`
  讀 `vNowMs`，而 `offlineFor` 會推它），但離線收益**不寫** `LOOT_STATS`。所以離線 16
  小時之後那一拍是「時間過了 57,600 秒、擊殺 0 隻」——速率被算成 0，每個離線日上線的
  頭五分鐘都會誤判成打不動並退關。中斷不是打不動，是沒在看：取樣間隔超過 `maxGapSec`
  就重新起算。
- **計數器要指到 `sources.field`**。`lootStats.kills` 的總數含塔戰 BOSS（js/tower.js），
  指到總數的話爬塔會被誤算成野外打得動。

## 裝等分段死鎖：AI 與真人差距的主因

### 症狀

極限策略、20 遊戲小時、10 個 seed：

| seed | 等級 | 最高關卡 | 停留關卡 | 物攻 |
| ---: | ---: | ---: | ---: | ---: |
| …070 | 54 | 50 | 42 | **334** |
| …072 | 56 | 50 | 42 | 582 |
| …076 | 54 | 50 | 42 | 245 |
| …078 | 50 | 50 | 42 | 503 |
| …079 | 51 | 50 | 41 | 448 |
| …071 | 80 | 100 | 90 | 7,708 |
| …075 | 88 | 100 | 82 | 21,810 |
| …077 | 55 | 100 | 100 | 3,368 |
| …073 | 65 | 119 | 119 | 10,260 |
| …074 | 134 | 141 | 140 | **34,983** |

**結果是雙峰的**：一半的 seed 卡在關卡 42 動不了 20 小時，另一半跨過關卡 50 之後
物攻差了兩個數量級。這不是運氣分佈，是兩個不同的穩態。

卡住那一組的最終存檔，13 個部位全部是「R4 史詩、**裝等 1**」，
而 299 件背包的 `maxLevel` 也是 1。物攻曲線在 7 小時之後**是往下走的**
（727 → 334）。

### 機制

三件事咬在一起：

1. `equipmentTierLevel`（`js/formula.js:1251`，`EQUIP_TIER_SIZE = 50`）：
   關卡 1~49 掉**裝等 1** 的裝備、50~99 掉裝等 50、100~149 掉裝等 100。
2. 詞條數值 `=（基礎值 + 成長基礎值 × 每級成長 × (裝等−1)）× 品質倍率`。實測 `atkFlat`：

   | | 裝等 1 | 裝等 50 | 裝等 100 |
   | :--- | ---: | ---: | ---: |
   | R4 史詩 | 12.0 | 335.4 | 665.4 |

   跨過關卡 50 是 **×27.95**；而同樣裝等 1 之下 R2 → R5 只有 7.0 → 16.0（**×2.29**）。
3. `stageGate` 的 `checkpoints` 把前期停在寫死的 `park` 區間，其中
   `maxStage: 50` 那一段是 **`[41, 45]`**——一個每一件掉落都是裝等 1 的區間。

於是形成閉環：

```
park [41,45] → 掉落永遠裝等 1 → 詞條只剩 base → 戰力上不去
  → 過不了關卡 50 守關 BOSS → 死了退關 → 品質覆蓋率閘門把它壓回 [41,45]
```

三道舊閘門（裝備品質覆蓋率、卡關重試、詞條缺口）一道都沒響，因為沒有一道在量
**「我停的地方掉得出比身上更好的裝備嗎」**。

### 為什麼換裝規則沒有救回來

舊的 `bestPerSlot` 用字典序 `[品質, 裝等, 太古數, 評分]`，**品質排第一**。
那等於用一個 ×2.3 的因子去否決一個 ×28 的因子：一件 R4 裝等 1 會把那個部位鎖死，
直到同品質的新裝等掉落為止。

原本的理由寫得很清楚也不算錯——「品質決定插槽數與附魔欄數，是換不回來的」。
問題是它被寫成了**否決權**而不是加分項。品質的價值（R4 三槽四詞條、R5 四槽五詞條）
在 `computeStats` 裡本來就算得到，不需要靠排在第一位來保護。

改成問遊戲「把它穿上去戰力是升是降」之後，插槽變少與強化歸零這兩件
`computeStats` 反映不了的成本，折算成一個**有界的門檻**（`socketPenalty` /
`upgradeGuard`），而不是否決。

### 這一節的教訓

> 「品質 > 等級 > 太古 > 評分」這條規則在 `player_strategy.md` 裡是對的——
> 它描述的是**真人心裡的排序**。翻譯成程式時被寫成字典序，於是一個
> 「通常成立的偏好」變成了「永遠成立的否決」。
>
> 策略文件寫的是傾向，程式寫的是規則。**把傾向翻譯成硬規則的那一步，
> 就是失真最常發生的地方**，而症狀永遠是「AI 卡住了」，不會是錯誤訊息。

## 邊際效益評估器：讓策略問得出「誰比較強」

### 為什麼需要第三層

策略層拿不到 `G`、`FIELD` 與任何遊戲函式，那是刻意的能力剝奪。代價是它**沒有辦法
評價任何東西**——它只能比較遊戲已經算好放進面板的數字。於是所有「哪個比較好」的
判斷都被迫寫成人工排序：詞條優先級清單、換裝的字典序、強化的品質上限表。

固定排序的問題不是排錯，是**這種形式表達不出正確答案**。實測本專案的面板：

| 詞條 | 邊際 ΔDPS |
| :--- | ---: |
| `atkFlat` | **+11.11%** |
| `hit` | +6.35% |
| `atkPct` | +2.96% |
| `critRate` | +1.90% |
| `critDmg` | **+0.52%** |

爆傷排最後，因為那一刻的暴擊率只有 5%——同一張表在暴擊率 60% 時會完全倒過來。

`scripts/sim/evaluator.js` 是這一層。它跑在**引擎的** vm context（看得到 `G`、
`FIELD` 與全部遊戲函式），把結果算成純資料經 `panels.eval` 交給策略沙箱。
策略仍然只做一件事：在一堆數字裡挑最大的。

```
run_sim.js ──決策點──▶ engine.panel('eval')
                          │  evaluator.js（引擎 context：有 G / FIELD）
                          │    computeStats(假設裝備) → 遊戲算的 ΔDPS / ΔEHP
                          ▼
                       純資料 ──▶ policy.decide(深拷貝) ──▶ 指令
                                    策略 context：仍然沒有 G / FIELD
```

三個沒有被放寬的地方：

| | 為什麼 |
| :--- | :--- |
| 隔離 | 策略拿到的仍然只是深拷貝的純資料，`test_policy_isolation.js` 12 項反證不受影響 |
| 沒有第二份公式 | 每一處算式都只由遊戲函式串接（`computeStats` / `defReduction` / `affixBaseValue`…） |
| 不出貨給玩家 | 放在 `scripts/sim/`，不是 `js/worker/`——這東西只有 AI 模擬器用得到 |

### 它算什麼

| 欄位 | 內容 |
| :--- | :--- |
| `combat` | `timeToKill` / `timeToDie` / `cause`（`DPS_TIMEOUT` 或 `EHP_TOO_LOW`）|
| `affixRoi` | 每條詞條多一條值多少 ΔDPS%／ΔEHP%（合成一件裝備再問 `computeStats`）|
| `equippedAffixes` | 身上每條詞條拿掉會掉多少——洗煉時「犧牲哪一格」的依據 |
| `slotUpgrades` | 每個部位換上背包最佳候選的真實戰力差 |
| `tier` | 裝等分段斷點與跨過去的增幅 |
| `resources` | 以遊戲當下報的成本為分母的資源水位 |

### 兩個必須一起講的限制

**1. DPS 模型只含普攻，低估約 5 倍。** 這對 ROI 無害（ROI 是比值，常數倍率會約掉），
但絕對時間會全錯。所以 `timeToKill` 一律先用遊戲自己的 `currentDps()`（最近 10 秒
實際傷害）校正模型尺度：模型負責「對屬性的敏感度」，遊戲負責「絕對值」。
`currentDps()` 還沒量到時回 `unknown`，**不猜**。

**2. 兩個係數是抄的。** 命中夾值（5%～100%）與探針強度取樣點在遊戲裡是內嵌在
`resolveHit` 的字面值，沒有具名函式可呼叫。`tests/sim-evaluator.test.cjs` 直接
比對 `resolveHit` 的原始碼當哨兵，而且 `run_summary.json` 的 `evaluator.model`
每一場都會揭露。

### 唯讀性是這裡最容易破的一件事

評估器要問「假如換上這件會怎樣」，用的是 `computeStats(override)`。踩過一次：
`itemScore()` 內部的 `itemEnchants()` 會把 `{ enchant: null }` **就地**正規化成
`{ enchants: [] }`——於是「看一下背包」這個純讀取動作改掉了存檔，
同 seed 的兩場雜湊不同，而症狀只是一串對不上的字串，完全看不出來是誰動的。

所以任何流進遊戲函式的背包物品一律先過 `evalSafeItem()` 複製。
`tests/sim-evaluator.test.cjs` 以「跑過評估器與沒跑過，存檔逐位元組相同」反證這件事。

### 效能：這個機制能不能開著跑，取決於這一節

| 版本 | 每次面板 |
| :--- | ---: |
| 初版 | 74 ms |
| `itemScore` 改成整份背包預先算一次（不要寫在 sort 的比較函式裡） | 30 ms |
| 詞條 ROI 先選宿主再精算一次（原本每個合法部位各精算一次） | 20 ms |
| 身上詞條只探 ROI 前三名的宿主部位（原本全身 13 個） | 13 ms |
| 規劃結果快取 `refreshSec` 遊戲秒（以 `GT` 為鍵，不是真實時間） | **6.7 ms** |

決策每 5 秒、20 遊戲小時＝ 14,400 次，最後的版本替一場 11 分鐘的模擬多加約 100 秒。

⚠️ **完整的 `panels.eval` 絕對不能排進 1Hz 觀測**。敗因診斷必須在死亡瞬間附近取樣，
所以另外有一個便宜的 `panels.evalCombat`（只做戰鬥側寫，不碰 `computeStats`，
0.02 ms）。`policy.profile.combat` 宣告成陣列時**只有第一條**會被加進觀測面板，
`tests/sim-evaluator.test.cjs` 有哨兵盯著 `eval` 沒有混進去。

### 第一版實測踩到的兩個坑（都已修，都不會有錯誤訊息）

第一版跑完 6 個 seed 之後有兩個 seed **退步**（最高關卡 100 → 51），
而它們的物攻反而變高（8,409 → 12,282）。「變強但推得更慢」這個組合正好指出兩件事：

**1. 進了安全區間就原地不動。** 舊的 `park` 語意是「低於下緣才往前推」，
對寫死的小區間（`[11,15]`）沒問題；但裝等分段把上緣拉到 99 之後，
原地不動就變成停在 51 整整六小時，而對照組同時間已經推到 89。
分段之內往前推是純賺——裝等不變，但關卡愈深品質擲骰愈好。
現在 `tierBand` 模式下目標是推到**上緣**。

**2. 資源門檻用了「最貴那件」當全體分母。** 金幣被寶石商店吃掉之後最貴那件變成
付不起，而整條強化規則是拿那一個數字當總開關——**一個部位付不起，全身十三個
部位一起停工**。實測那一場跑到第 20 小時握著 **157,034 碎片沒有用掉**。
改成逐部位判定：付得起的就投，付不起的略過那一格。

> 兩個坑是同一種形狀：**把一個局部的限制寫成了全體的開關**。
> 這類錯誤在報表上永遠看起來像「AI 很保守」，不會像 bug。

### 第三個坑：整段裝等分段被無條件放行（獨立驗證抓到的）

前兩個坑是自己找到的，這一個不是——是 Codex 拿**沒有被挑選過**的 8 個 seed
重跑 A/B 抓到的（`docs/ROI_AGENT_VERIFICATION_2026-08-03.md`）。
7 個 seed 大幅改善，但 seed `20260903` 崩掉：

| | 等級 | 最高關卡 | 物攻 | **死亡** |
| :--- | ---: | ---: | ---: | ---: |
| 舊策略 | 86 | 100 | 4,653 | **33** |
| ROI 第一版 | 57 | 50 | 477 | **1,126** |

死亡數是關鍵：20 小時死 1,126 次，平均每 64 秒一次。角色被推到分段深處反覆送死，
撿不到裝備、也跨不過裝等斷點——**這個機制擋掉了它自己要促成的那件事**。

原因在 `tierPush` 的這一句：

```js
if (!behind && gain >= minGain) passGate = true;   // ← 沒有任何存活條件
```

`behind` 的定義是「身上裝等落後於當前分段能掉的」。但在**第一個分段**（關卡 1~49）
裡，掉落的裝等恆為 1，身上的自然也是 1，所以 `behind` 永遠是 false——
整段被無條件放行，一路推到分段底。三道舊閘門加上新的裝等閘門，
**沒有一道在問「你打得動嗎」**。

修法是新增上限型目標（`atMost`，原本只有 `atLeast`）：

```json
{ "id": "deathRate", "kind": "ratePerMin",
  "counter": "panels.battle.lootStats.sources.field.deaths",
  "windowSec": 600, "atMost": 0.5 }
```
```json
"tierPush": { "advanceRequiresTargets": ["deathRate"] }
```

只擋**前進**，不強迫後退——後退交給遊戲自己的死亡退關與 park 下緣，
這一層的退關來源已經有兩個，再加一個只會讓歸因變難。

> 第一次修在錯的地方：只把條件加在「分段之內往前走」那條路徑上，
> 而實際失控的是「放行推關」那一條。測出來完全沒有效果。
> **兩條前進路徑都要管**——這件事只有把測試寫成「餵一個超標的死亡率進去，
> 看閘門會不會關」才驗得出來，讀程式碼讀不出來。

### 門檻與快取間隔的實測掃描（8 seed × 20 小時，同一組 seed）

| 版本 | 等級 最小/中位 | 關卡 最小/中位 | 物攻 最小/中位 | 縮時 |
| :--- | ---: | ---: | ---: | ---: |
| 舊策略 | 54 / **80.5** | 50 / **100** | 302 / **6,511** | 296x |
| 無死亡閘門 | 57 / **132.5** | 50 / **148** | 477 / **36,966** | 165x |
| **死亡率 ≤0.5、refresh 15s** | **116 / 158** | **136 / 150** | **39,960 / 59,753** | **187x** |
| 死亡率 ≤0.8、refresh 15s | 112 / 172.5 | 130 / 150 | 16,032 / 66,474 | 134x |
| 死亡率 ≤0.8、refresh 45s | 51 / 137.5 | 50 / 142.5 | 346 / 48,735 | 222x |

兩個可以直接讀出來的結論：

- **0.8 的中位比 0.5 高，但下緣掉了 2.5 倍**。這次改造要修的就是下緣崩掉的失效模式，
  所以取下緣，選 0.5。
- **`refreshSec` 從 15 拉到 45 會讓整個下緣崩回原點**（物攻最小值 39,960 → 346、
  關卡最小值 136 → 50），換到的只有縮時 187x → 222x。規劃太舊比算得慢更貴。

### 效能：那道 70% 的門檻是錯的門檻

驗證任務裡訂了「ROI 的縮時倍率不得低於舊策略的 70%」，實際是 **63%**。

實測評估器在真實深度狀態（Lv.221／關卡 150／背包 303 件）的成本：

| | 每決策點 |
| :--- | ---: |
| 只跑模擬 | 6.74 ms |
| 加上完整 `panels.eval` | 22.19 ms |

評估器確實佔了七成——而且**不是因為跑得比較深**：舊策略自己在關卡 50 到 140 之間
縮時倍率一直是 257~332x，深度本身不影響。

但唯一達到 70% 的設定（refresh 45s）**把改造要修的失效模式整個放了回來**。
達標會是自欺，所以維持 63% 並在這裡揭露。要再快就得從
「整份背包每次重算 `itemScore`」下手（快取 id→分數），那是還沒做的事。

## 觀測與行動是兩種節奏

| 參數 | 意義 | 是否隨玩家強度變化 |
| :--- | :--- | :--- |
| `decideEveryGameSec` | 玩家多久做一次後勤（換裝、洗詞條、鑲寶石…） | 是（輕度 60s ～ 極限 5s） |
| `observeEverySec` | 玩家多仔細看戰鬥 | **否**，預設一律 1 秒 |

> 這兩件事原本是同一個旋鈕。後果是玩得少的人連戰鬥觀測都變粗——而卡關重試間隔正是
> 「觀察到的敵人殘血百分比當分鐘數」（`retryAt = now + max(10, minHpPct) × 60`），
> 於是低強度玩家被**系統性地多罰一次**。真人盯著螢幕看到的戰鬥細節，
> 不會因為他今天只上線兩小時就變粗。

實測（seed=4242，3 遊戲小時，全程不送指令，所以遊戲演進完全相同，差異純粹來自觀測）：

| 取樣間隔 | 偵測到的失敗次數 | 平均推導重試間隔 |
| :--- | ---: | ---: |
| 1s（接近真人） | **61** | 39.1 分 |
| 15s（重度） | 31 | 40.5 分 |
| 60s（輕度） | **33** | **64.0 分** |

兩個效果疊在一起：60 秒取樣**漏掉近一半的失敗**（整場交戰落在兩次取樣之間，
那一關根本沒被記成卡點，針對性強化與重試閘門完全不會啟動），看到的殘血還偏高，
重試間隔被拉長 1.6 倍。

`--observe-every=N` 可覆蓋；設成與 `decideEveryGameSec` 相同即還原拆分前的行為
（實測輕度玩家 `--observe-every=60` 精確重現舊雜湊）。

實作上，觀測走 `policy.observe(state)` 這個獨立進入點，隔離方式與 `decide` 完全相同，
且只建 `observePanels`（從 `track.monster` / `track.stage` 與速率目標的 `counter` 推導）
——**不含背包面板**，否則 1Hz 觀測會變成每秒建一次背包，那是這個設計最容易踩的效能陷阱。

## 線上／離線班表

策略以 `dailyActiveHours` 宣告每日遊玩時數，驅動端據此在**在線模擬**與**離線結算**
之間切換。每個 24 小時週期先連續在線該時數，其餘時間離線。

> 在 2026-08-01 之前這個欄位是死的：四份強度策略都宣告了，但 `createPolicy()` 沒有
> 把它轉出來、`run_sim.js` 也沒有讀。四種強度全部被當成 24 小時不間斷在線，
> 只有決策頻率不同——輕度玩家被模擬成一個永不睡覺、每 60 秒操作一次的人。

**⚠️ 啟用班表後 `--hours` 是牆鐘時間（含離線）**，不是線上時數。
`run_summary.json` 的 `schedule.onlineHours` 才是實際跑了模擬的時數，兩者不可混用。

`--ignore-schedule` 忽略宣告值、全程在線，用來重現班表實作前的行為。

### 離線與線上是完全不同的兩套模型

離線收益一律由遊戲的 `applyOfflineProgress`（`js/save.js`）計算，harness 不碰任何公式。
它是**固定費率**的，與角色實際 DPS 無關：

| 常數（`js/formula.js`） | 值 | 意義 |
| :--- | :--- | :--- |
| `OFFLINE_KILL_INTERVAL` | 20 秒 | 每 20 秒殺 1 隻菁英怪 |
| `offlineStageFor(best)` | `⌊(best−10)/10⌋×10` | 打的是比最高關卡低 10~19 關的菁英 |
| `OFFLINE_MAX_HOURS` | 24 | 收益上限；未滿 1 分鐘不計 |

`sim/engine.js` 的 `offlineFor(sec)` 照真實流程走：`stampSavedAt()`（等同關掉遊戲時
的落地）→ 推進虛擬時鐘但不跑 `simStep` → 呼叫 `applyOfflineProgress()` 的同步路徑。

### 實測：班表讓四種強度終於分得開

48 小時牆鐘、seed=777、全新角色：

| 強度 | 每日在線 | 實際在線 | 最終等級 | 最高關卡 |
| :--- | ---: | ---: | ---: | ---: |
| 輕度 | 2h | 4h | Lv.48 | 50 |
| 中度 | 4h | 8h | Lv.50 | 50 |
| 重度 | 8h | 16h | Lv.56 | 50 |
| 極限 | 24h | 48h | Lv.64 | 115 |

同一份輕度策略若用 `--ignore-schedule`（＝班表實作前的行為）會跑到 **Lv.76 / 關卡 70**，
比實際高出 28 級。**先前所有輕度與中度的模擬數據都要重跑。**

兩個值得注意的現象，都是這張表第一次看得到的：

1. **輕度與中度幾乎沒差**（Lv.48 vs Lv.50）。離線收益是線性費率且遠未達 24 小時上限，
   輕度玩家離線更久、離線收益反而更多（7,920 vs 7,200 隻），把在線時數的差距抵銷掉了。
2. **前三種強度全部卡在關卡 50**，只有極限玩家過得去。那正是
   `player_strategy.md` 寫的 50 級守關 BOSS。

## 真人基準線：錄一場真人的，拿去跟 AI 的相減

### 為什麼需要這個

「AI 跑起來跟真人有落差」在這條管線出現之前是一句沒辦法追下去的話——只有 AI 那條
曲線有數字，真人那條沒有。要調策略、要判斷 `player_strategy.md` 哪一段翻譯失真，
都得先有真人那條線。

### 三個步驟

**1. 錄**　起伺服器（`啟動數值模擬器.bat` 或直接跑 `node tools/sim_server.cjs`，
它本來就有靜態託管），以決定論模式開遊戲，正常玩：

```
http://127.0.0.1:28342/index.html?seed=777&record=1
```

必須走 `http://127.0.0.1`，不能用 `file://`——錄製器與決定論模式都只認本機 hostname。

右下角會出現「● 錄製中」的徽章，顯示已錄到幾道指令、幾筆樣本。玩完按「匯出軌跡」
下載 JSON。可選 `&rowEvery=N` 調整樣本密度（預設每 10 則 tick 一筆）。

錄到的東西有三樣：起始存檔、指令軌跡（含**執行當下**的 `simT`）、實測 view 樣本。

**2. 驗**　證明軌跡是完整的——漏一道指令不會有任何錯誤訊息：

```bash
node scripts/verify_trace.js human_trace_seed777_....json
```

它用同一份存檔、同一個 seed 重播軌跡，再與錄製當下的實測樣本逐檢查點比對。
PASS 同時證明了三件事：軌跡沒漏指令、時間戳精確到步、headless 忠實於瀏覽器。
做這一步建議用 `&rowEvery=1` 錄一段短的（幾分鐘），檢查點最密。

**3. 比**　把真人那一場跑成標準輸出，再與 AI 的相減：

```bash
node scripts/run_sim.js --trace=human_trace_seed777_....json --out=sim_out_human
node scripts/run_sim.js --policy=scripts/sim/policy.moderate.json --seed=777 --hours=3 --out=sim_out_ai
node scripts/compare_runs.js sim_out_human sim_out_ai
```

`--trace` 走的是同一支 `run_sim.js`、同一組快照欄位、同一份 `run_summary.json` 格式，
所以兩邊的輸出天生可以相減。這也是軌跡重播刻意不另寫回放腳本的原因——第二套報表
遲早會跟第一套長歪，而長歪的那一刻沒有人會發現。

### 精確的時間戳是怎麼拿到的

指令是非同步的，主執行緒自己蓋的時間戳一定是糊的，而糊掉的軌跡重播出來會是另一場
（亂數序列錯開一步，之後每一次掉落都不同）。

關鍵在 `js/worker/sim.worker.js` 的 `MSG_IN.CMD` 分支：指令成功後 Worker 會**立刻補送
一則 tick**。Worker 的 `onmessage` 是同步的，ACK 與那則 tick 之間插不進任何東西，
所以「ACK 之後收到的第一則 tick」的 `view.simT` 就是指令執行當下的模擬時鐘，精確到步。

因此錄製器不需要自己算時間——精確的時間本來就在訊息流裡。
（唯一需要協議配合的是 `simT` 這個欄位本身，見 v14；`gt` 在戰鬥暫停時會停住，
當不了對齊軸。）

| 檔案 | 角色 |
| :--- | :--- |
| `js/recorder.js` | 錄製器本體。只在本機 `?record=1` 時做事，正式遊玩是空殼 |
| `js/bridge.js` | 兩個鉤子：`send()`（操作的唯一出口）與 `start()`（起始存檔） |
| `scripts/sim/trace.js` | 把軌跡包成與 `sim/policy.js` 相同的決策來源介面 |
| `scripts/sim/viewdiff.js` | `cross_check` 與 `verify_trace` 共用的比對判定 |

### 已知限制（不要在報告裡略過）

- **協議 v14 之前錄的檔**只能退回以 `gt` 對齊，而 `gt` 在戰鬥暫停時會停住，
  那種錄製只要暫停過就重播不出來（`run_summary.json` 的 `trace.axis` 會是 `gt`，
  `verify_trace.js` 會在比對前先警告）。用目前版本重錄即可，v14 起以 `simT` 對齊，
  暫停已經不是限制——實測：暫停 2 次共 89 個 tick、`gt` 與 `simT` 差 17 秒，
  332 個檢查點仍然完全一致。
- **同一個 tick 內連送的多道指令**會共用同一個刻度（一步 0.1 秒，人手連點兩下必定同步），
  但那一種重播會在同一步依序送出、完整重現，**不是問題**。
- **錄製不會動到你的存檔**（2026-08-01 起）。決定論模式下 `requestPersist` 會擋掉所有
  非自願的落地（`auto` / `folder` / `shutdown`），只有明確按下手動存檔或重新開局才會寫。
  在此之前 `onVisibility` 的 `SHUTDOWN` 沒有被擋，錄製期間切一次分頁就會蓋掉
  `auto_current`——如果你用的是舊版本，錄製前請先備份。
- **軌跡重播每步都問一次決策**（`decideEveryGameSec` = 一步），所以 `engine.view()`
  的呼叫次數是一般策略跑的一百多倍。它會順帶呼叫 `updateShownRes()`，讓重播存檔的
  `shownRes` 旗標比瀏覽器那份早一點被點亮。`shownRes` 不在 `buildView()` 的輸出裡，
  不影響逐點比對，但會影響最終存檔雜湊。
- **真人錄製只有幾小時**，`compare_runs.js` 只比重疊區間，不外插。
