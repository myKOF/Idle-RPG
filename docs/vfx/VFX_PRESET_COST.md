# 特效效能成本（Preset Cost）

VFX Editor 每個預覽視窗的右上角顯示一個值：**這一份特效在實機上大概多重**。
超過門檻轉橘色。2026-10-01 使用者要求：做特效時當場就要看得到，不要等戰場塞滿才發現。

算法只有一份：`tools/vfx/preset-cost.cjs`（編輯器、測試、之後的 CLI 共用）。

## 這個值是什麼

```
估算值（ms／幀） = 峰值節點數 × 3.9µs  ＋  填色覆蓋（幾個畫面）× 21µs
```

**它是估算，不是量測。** 從 Preset 資料推算，不跑 Core、不看畫面，所以立刻算得出來、
也不受預覽播到第幾秒影響。

## 係數是哪來的

全部來自 2026-09-30 的實機量測（GTX 1050、畫布 670×643，見 `docs/AI_TASKS.md` 的 FPS 調查）：

| 係數 | 值 | 來源 |
| --- | --- | --- |
| 每個節點每幀 | 3.9µs | 拆解：Core 0.64（16%）＋ Pixi 後端寫入 1.1（28%）＋ Pixi 渲染 2.1（55%） |
| 變形圖層（Mesh）加權 | ×2.5 | 頂點每幀重算且不進批次。沒有單獨量過，取保守值 |
| 填滿一個畫面 | 21µs | 60 份大面積加色 preset 疊在同處約 10ms，那一類每份覆蓋約 8 個畫面 |
| 橘色門檻 | 0.25ms | 素材庫中位數 0.047ms、p90 0.22ms；門檻以上約佔 8% |

那次調查的結論是 **成本 ≈ 節點數**：同屏 17,692 個節點時 Core 一幀 51ms、FPS 7；
換容器（ParticleContainer）整體只快約 1.5 倍，**槓桿是減少節點數**。所以這個值的主體就是節點數。

## 怎麼算峰值節點數

重點是「同時」兩個字：各圖層的峰值**不在同一個時刻**，不能相加。
所以把整段時間軸以 1/60 秒取樣，每一刻把各層當下活著的節點加起來，取最大值。

| 圖層 | 當下的節點數 |
| --- | --- |
| sprite／procedural | delay 到 delay+duration 之間算 1（loop 的一直都在） |
| particle `burst` | count 顆一起出生，之後照壽命範圍逐漸凋零 |
| particle `rate` | 穩態＝發射率 × **平均**壽命；停止發射後再過一個平均壽命才清空 |
| particle `sub` | 母層「最近一個子壽命內死掉／出生的那些」× count |
| empty | 0（它只是父物件） |

每層再夾 `maxParticles`（沒填就是遊戲的 `perEffectParticleLimit` 2000）。

**準確度**：`tests/vfx-preset-cost.test.cjs` 的 COST-1 拿真的 Core 跑過全部 236 份 preset 對答案，
六成以上完全命中，其餘都在 ±25% 或差 1 個節點以內。對照 2026-09-30 的價格表：
ground-storm-dance 實測 1.10／估 1.21、ground-blizzard 0.70／0.64、icearrow-frost 0.45／0.45、
burst-icearrow-crystal 0.29／0.30。

## 已知偏保守的地方

都會寫在提示卡的「※」裡：

- `scaleOverLife` 把圖放大的部分沒有算進填色
- 序列幀、遮罩、著色器的差異一律當成一般 sprite
- 查不到素材尺寸時填色用 256px 估

## 怎麼看這個值

滑到那個值上面會展開明細：圖層數與型別、峰值節點（粒子幾顆）、CPU 與填色各佔多少、
繪製批次幾批、最重的幾層是哪幾層。

兩個判讀重點：

- **「同時 N 份就吃滿一幀」** 比 ms 本身好懂。0.45ms 聽起來很小，但那代表場上同時 37 份就滿了，
  而連鎖類技能很容易同時幾十份——2026-09-30 的 FPS 7 就是這樣來的（每秒 172 個爆點）。
- **覆蓋很多個畫面** 的那種（大面積加色）節點數可能只有 1，CPU 很便宜，但疊起來吃的是 GPU。
  提示卡會另外標一行。

要再便宜，順序是：先砍粒子數（節點數是主體）→ 再看大面積加色的層數 → 最後才是 blendMode 的批次。
