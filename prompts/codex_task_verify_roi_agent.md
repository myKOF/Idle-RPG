## 具體工作內容

### T1 — 回歸：既有策略是不是真的一行行為都沒變

改造動到的是**共用**程式碼（`policy_interpreter.js` 的 `observeCombat` /
`updateContext` / `stageGate`，以及 `engine.js` 會把 `evaluator.js` 載進 vm context）。
共用路徑的改動最容易的破法是「順手改了預設值」與「新宣告的函式名蓋掉遊戲的同名函式」，
兩者都不會報錯。

用**存檔雜湊**驗，不要看終端摘要——摘要只有等級與關卡，蓋不住細節。

```bash
git worktree add ../verify_base d1c7c1e     # 改造前的父 commit
```

對 `policy.default / light / moderate / heavy / extreme / lategame` 六份 × seed
`4242, 777, 20260803` 各跑 **2 遊戲小時**，比對兩邊 `run_summary.json` 的
`determinism.finalStateHash`。

- **通過條件**：18 組**全部**逐位元組相同。
- 有任何一組不同：那一組就是回歸，記下 policy + seed，跑
  `node scripts/compare_runs.js <base輸出> <新輸出>` 找分岔點並回報。

提出者只跑了 `extreme` 與 `light` 各 2 個 seed，其餘四份沒跑過。

### T2 — 評估器的唯讀性（獨立重現，不要只跑既有測試）

`tests/sim-evaluator.test.cjs` 已經有這一項，但它是提出者自己寫的。請**另外**寫一段
一次性腳本獨立驗：同一個 seed 跑兩場，一場每 30 遊戲秒呼叫一次
`engine.panel('eval')` 與 `engine.panel('evalCombat')`、一場完全不呼叫，
比對 `engine.saveJson()` 的完整字串（不是雜湊，要能指出差在哪個欄位）。

背景：這一項踩過一次。`itemScore()` 內部的 `itemEnchants()` 會把背包物品的
`{ enchant: null }` **就地**正規化成 `{ enchants: [] }`，於是「看一下背包」
這個純讀取動作改掉了存檔。修法是 `evalSafeItem()` 複製，請確認沒有漏網的路徑
（`evalItemPlusAffix` / `evalItemSwapAffix` / `evalEquippedAffixValue` 也都碰物品）。

順便檢查 vm context 的名稱衝突：`evaluator.js` 用 `vm.runInContext` 載進**引擎**的
context，它宣告的每個 function 都會掛上該 context 的 global。列出 `evaluator.js`
所有頂層宣告，確認沒有一個與遊戲既有的全域函式同名（同名會靜默覆蓋遊戲的實作）。

### T4 — 在**沒有被挑選過**的 seed 上重跑 A/B（本任務最重要的一項）

這一項回答宣稱 C 的偏誤。用**你自己挑的**、與提出者那 6 個無關的 seed：

```bash
node scripts/run_batch.js --hours=20 --seeds=<你挑的 8 個 seed> \
  --policy=scripts/sim/policy.extreme.json,scripts/sim/policy.extreme.roi.json \
  --out=sim_ab_verify
```

seed 怎麼挑請寫進報告（例如「取 20260901~20260908 連號」），
**挑好之後不准因為結果不好而換一批重挑**——那會把驗證變成挑選。

比對四個指標的**最小／中位／最大**：最高關卡、等級、物攻、最終停留關卡。

- **通過條件**：中位數在四個指標上都不劣於舊策略，且**最小值明顯提升**
  （改造主要修的是下緣：舊策略最差的一場物攻 411，新策略最差 20,117）。
- 中位持平但下緣提升 → 仍算通過，但要在報告裡明說「這是收斂，不是整體提升」。
- 有 seed **退步** → 記下 seed，把兩邊的 `snapshots.csv` 逐 2 小時列出
  （關卡、等級、物攻、碎片），標出從哪一小時開始分岔。

背景參考：第一版改造就是這樣抓到兩個退步的 seed 的——它們「物攻變高但關卡變低」，
`snapshots.csv` 顯示第 14 小時踏進關卡 51 之後**六小時原地不動**、碎片累積到 157,034
沒有用掉。那兩個坑已修（`docs/SIM_HARNESS.md`「改出來的兩個坑」），
但同一類錯誤（把局部限制寫成全體開關）可能還有第三個。

### T5 — 效能

`run_summary.json` 的 `performance` 有實測縮時倍率。比對 T4 兩組的中位倍率。

- 提出者宣稱新策略每決策點多花約 6.7 ms，20 小時約 +100 秒。
- **通過條件**：新策略的縮時倍率不低於舊策略的 70%。低於就回報，
  並附上 `panels.eval` 的 `planAgeSec` 分佈（那個欄位是規劃快取的年齡，
  若它經常等於 0 就代表快取沒有生效）。
